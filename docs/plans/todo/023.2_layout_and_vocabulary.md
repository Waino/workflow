# 023.2: Path layout layer and worktree/repo vocabulary

Input: `intent/023_out_of_band`, `planning/023.1_project_metadata_file`
Completeness: complete — pure refactor; no user-visible behaviour change except the `config.yaml`
key rename.

## Goal

Today `project_dir / repo` (≈70 sites) simultaneously means four different things: the root of a git
repo, the root of the plans tree, the root of the venv, and the root of the pre-commit hook. In oob
mode these are different directories. `RepoName` also carries two meanings that become disjoint in
oob mode: the four agent-side clones (`canon`, `planner`, `builder`, `reviewer`) and the actual git
repos (`docs`, `mypackage`, `dep1`).

Land the path abstraction and the vocabulary split *first*, as a refactor with the existing test
suite green, so that later oob bugs cannot be confused with path-abstraction bugs.

## Scope

In scope:
- New `workflow/layout.py`: `Layout`, implementing the path math for **both** modes.
- Replace every `project_dir / <worktree>` join outside `layout.py` with the appropriate accessor.
- Rename `RepoName` → `WorktreeName` and the parameters/fields that mean "one of the four clones".
- Rename the `config.yaml` key `repo_override` → `worktree_override` (+ migration step).

Out of scope: creating oob projects, `--oob`, multi-repo git operations, validate/doctor behaviour
changes. `Layout`'s oob branches are exercised by unit tests only until 023.4.

## Design

### `workflow/layout.py`

```python
DOCS_REPO = "docs"   # the repo holding docs/plans; in in-band mode, the project's single repo

class Layout(BaseModel):
    project_dir: Path
    metadata: ProjectMetadata

    # --- directories ---
    def worktree_root(self, worktree: WorktreeName) -> Path
    def git_repo_root(self, worktree: WorktreeName, repo: str = DOCS_REPO) -> Path
    def plans_root(self, worktree: WorktreeName) -> Path
    def venv_root(self, worktree: WorktreeName) -> Path
    def hook_root(self, worktree: WorktreeName, repo: str = DOCS_REPO) -> Path
    def bare_repo(self, repo: str = DOCS_REPO) -> Path

    # --- inventory ---
    def repos(self) -> list[str]          # in_band: [DOCS_REPO]; oob: [DOCS_REPO, *code_repo_names]
    def code_repos(self) -> list[str]     # in_band: [DOCS_REPO]; oob: code repos only
    @property
    def plans_prefix(self) -> PurePosixPath  # "docs/plans" in_band, "plans" in oob
```

Semantics:

| accessor | in-band | oob |
|---|---|---|
| `worktree_root(wt)` | `{project}/{wt}` | `{project}/{wt}` |
| `git_repo_root(wt, repo)` | `{project}/{wt}` (rejects a non-docs `repo`) | `{project}/{wt}/{repo}` |
| `plans_root(wt)` | `{project}/{wt}/docs/plans` | `{project}/{wt}/docs/plans` |
| `venv_root(wt)` | `{project}/{wt}` | `{project}/{wt}` |
| `hook_root(wt, repo)` | `= git_repo_root` | `= git_repo_root` |
| `bare_repo(repo)` | `{project}/bare` (rejects a non-docs `repo`) | `{project}/bare/{repo}` |

`plans_root` is deliberately identical in both modes — that is the property the oob layout was
designed for. What differs is the plan path **relative to its git repo**: `docs/plans/...` in-band
vs `plans/...` in oob, hence `plans_prefix`. Every `git add`/`git mv`/pathspec/`--name-only` consumer
must use `plans_prefix`, never a hardcoded `"docs/plans"`.

`venv_root` and `worktree_root` coincide in both modes; they are separate accessors because they are
separate concepts and the venv location is the thing 023.4 has to reason about.

Construction: add `WorkflowConfig.layout` (a method or cached property) that builds `Layout` from
`project_dir` + `metadata`, raising `WorkflowError` when either is `None` (reuse the wording of
`_require_project_dir`). Commands take `layout` from the config rather than re-deriving paths.

### Call-site conversion

Mechanical, one accessor per meaning. Representative conversions:

- `workflow/state.py:55` `project_dir / repo_name` → `layout.git_repo_root(worktree)`; the
  `docs/plans/...` relative paths handed to `git_mv` become `plans_prefix`-based.
- `workflow/plan_resolver.py:155` → `layout.plans_root(worktree)`; the `:(glob)docs/plans/...`
  pathspecs in `_git_newest_touch` and the `--name-status` parsing in `_parse_git_log_output` →
  `plans_prefix`; the git repo it runs `git log` in → `layout.git_repo_root(worktree)`.
- `workflow/validate.py:81` → `layout.git_repo_root(worktree)`.
- `workflow/commands/doctor.py:205,210` → `layout.bare_repo()` / `layout.worktree_root(wt)`.
- `workflow/commands/workflow.py`: all `project_dir / RepoName.x` → `layout.git_repo_root(WorktreeName.x)`;
  `project_dir / repo_name / ".venv"` → `layout.venv_root(wt) / ".venv"`;
  `project_dir / RepoName.canon / "docs" / "plans" / state` → `layout.plans_root(WorktreeName.canon) / state`.
- `workflow/commands/agents_md.py:56` → `layout.worktree_root(WorktreeName.canon) / "AGENTS.md"`
  (AGENTS.md lives at the worktree root in both modes; 023.4 changes where its *body* comes from).
- `workflow/tmux_dispatch.py:165,270-275` → `layout.worktree_root(...)` / `git_repo_root(...)`.

Project-root-relative files stay direct joins on `project_dir` and are **not** layout accessors:
`config.yaml`, `.workflow.json`, `.agents_md_hash`, `env.list`, `workflow.log.jsonl`,
`run_agent_in_docker.sh`.

Completion criterion: `rg 'project_dir\s*/\s*(repo|worktree|agent|RepoName|WorktreeName|"canon")'`
returns hits only inside `workflow/layout.py`.

### Vocabulary rename

`WorktreeName` = one of the four clones. Plain `str` repo names (`docs`, `mypackage`) are validated
against `.workflow.json`, not an enum — they are per-project.

| before | after |
|---|---|
| `names.RepoName` | `names.WorktreeName` (members unchanged) |
| `ScriptCommand.repo_override` | `ScriptCommand.worktree_override` |
| `ScriptCommand.pull_target` | unchanged name, retyped `WorktreeName` |
| `validate.infer_target_repo`, `target_repo_override` | `infer_target_worktree`, `target_worktree_override` |
| `plan_resolver.find_all_plans_in_repo(project_dir, repo)` | `find_all_plans_in_worktree(layout, worktree)` |
| `plan_resolver._Constraint.repos`, `git_provides_repo` | `.worktrees`, `git_provides_worktree` |
| `state.transition_plan(..., repo_override=)` | `worktree_override=` |
| `tmux_dispatch` target `repo_name` | `worktree_name` |
| `doctor.RepoCheck`, table column `repo` | `WorktreeCheck`, column `worktree` |
| local `repo_path` variables | `git_repo_root` / `worktree_root` per meaning |

`repo_override` is a key in every project's `config.yaml`, so add migration step 2 to
`scripts/migrate_023.py`: rewrite `repo_override:` → `worktree_override:` in the project's
`config.yaml` (text substitution on the key, reported per occurrence; skip if none). Update
`docs/default_config.yaml` and `docs/source/cli.rst` accordingly. Do **not** accept the old key in
the model — a pydantic alias would be exactly the maintained backwards compatibility this series is
avoiding.

## Risks

1. **Diff size.** This touches nearly every module and test. Keep it strictly mechanical; resist
   drive-by improvements, which would hide real changes in the noise.
2. **`plans_prefix` misses.** A forgotten hardcoded `"docs/plans"` is invisible in in-band mode and
   breaks only in oob. Grep for the literal after the refactor; the only permitted occurrences are in
   `layout.py`.
3. **`config.yaml` key rename** breaks every existing project until the migration script runs. The
   pydantic error for an unknown key must be clear; consider a `model_validator` that detects a
   leftover `repo_override` key and names the migration script.
4. **`find_all_plans_in_worktree` signature change to take `layout`** ripples into `doctor` and the
   resolver's many callers. Passing `layout` (rather than `project_dir`) is the point: it is what
   carries the mode.
