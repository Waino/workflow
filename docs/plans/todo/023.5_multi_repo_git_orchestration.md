# 023.5: Multi-repo git orchestration (`sync`, fetch-all, push-ahead-of-bare)

Input: `intent/023_out_of_band`, `planning/023.4_init_oob_and_bootstrap`
Completeness: complete

## Goal

In oob mode a handoff spans several git repos. `check` and `accept` must push every repo the agent
committed to; every command that hands work over must leave all repos fetched so the next agent
cannot start from stale code; and `bare/<code repo>` must be refreshable from upstream, which nothing
currently does.

## Scope

In scope: the ahead-of-bare push set for `check`/`accept`, per-repo pre-commit hook invocation,
fetch-all before prompt dispatch and handoffs, all-repos dirty preconditions, the new `workflow sync`
command, and the bare-staleness doctor note.

Out of scope: `validate`, the doctor rework, the `info` matrix, plan frontmatter (023.6). Docs-repo
branch lifecycle is unchanged — `plan/*` and `feat/*` branches, `transfer_branch_to_main`,
rebase-before-accept all keep operating on the docs repo only.

## Design

### What is a "repo that changed"

New helper in `git_helpers.py`:

```python
def git_commits_not_in_bare(repo_path: Path) -> int:
    """Number of commits reachable from HEAD but from no bare remote-tracking ref."""
    # git rev-list --count HEAD --not --remotes=bare
```

Counting against `--remotes=bare` (rather than `bare/<branch>`) is what makes a brand-new branch work:
its commits are simply not reachable from any bare ref. Callers must `git fetch bare` first.

`check`/`accept` compute the push set as `[repo for repo in layout.repos() if git_commits_not_in_bare(...) > 0]`
in the acting worktree, print a summary table (repo, branch, commits) as part of the resume preview,
and push each with `git_push_branch(repo_path, branch)`. No plan parsing is involved (decision 12).
The docs repo keeps its existing dedicated steps (transition commit, transfer to main); code repos get
one push step each, named `f"push {repo}"`.

`todo`, `implement`, `reject` push only the docs repo, as today.

### Branch handling in code repos

The tool does not manage code-repo branches (intent, "Git branch model"). Concretely:

- never `refresh_main`, `park_on_main`, or checkout in a code repo — a code repo's default branch may
  not even be called `main`, and the agent may be mid-work;
- `_sync_repos_best_effort` keeps its current behaviour for the docs repo and, for code repos, does
  `git fetch bare` only;
- on `check`, the reviewer's code repos are fetched, not checked out (decision 13). The reviewer
  agent checks out the branches named in the plan's frontmatter.

### Fetch-all

`tmux_dispatch`'s pre-prompt git sync (currently `git_pull` + `refresh_main` per worktree) becomes:
docs repo → unchanged pull/refresh; every code repo → `git fetch bare`. Failures stay warnings, as
today. This is the single most valuable line of defence against an agent working from stale code, so
it must cover *every* prompt dispatch, not just handoffs.

### Dirty-tree preconditions (decision 17)

`check` (and `accept`) gain a precondition over all repos in the acting worktree:

- **tracked** modifications (`git status --porcelain --untracked-files=no`) → hard failure listing
  repo and files: the agent has uncommitted work that would not be reviewed;
- **untracked** files → warning only. Third-party repos routinely carry untracked build output, and a
  hard failure there would be unactionable.

Reuse `git_status_porcelain`, adding an `untracked: bool` parameter rather than a second helper.

### `workflow sync`

New script command (project-level, like `doctor`; no state entry). Refreshes `bare/<repo>` from
upstream so agents' bases exist in bare:

```
workflow sync [--repo NAME]... [--branch NAME]...
```

Per repo (default: all repos in `.workflow.json`, plus `docs` if it has an upstream remote):
1. skip repos with no remote other than `bare`;
2. `git fetch origin --prune` in `canon/<repo>`;
3. resolve the upstream default branch `D` from `refs/remotes/origin/HEAD` (fall back to `main`, then
   `master`, and fail with a clear message if neither exists);
4. `git push bare "+refs/remotes/origin/{D}:refs/heads/{D}"` for `D` and each `--branch`.

Deliberately **not** mirroring all upstream heads: a forced mirror would clobber an agent's pushed
feature branch whenever upstream happens to have the same branch name. Syncing the default branch
covers the realistic "base my work on current upstream" case; `--branch` handles the rest explicitly.

Print per repo what moved (old → new sha) and support `--dry-run`.

### Doctor note

Add one informational note (not an anomaly): for each code repo, if `canon/<repo>`'s
`refs/remotes/origin/{D}` is ahead of `bare/{D}`, note `"bare is N commits behind upstream; run workflow sync"`.
It is a note rather than an anomaly because being behind upstream is normal between syncs.

### Per-repo pre-commit hook on `check`

`check` currently runs the sandbox pre-commit hook once for the builder worktree. In oob mode it runs
once per repo in the push set where `run_hook` is true, invoking the docker script's `hook`
subcommand with `--repo NAME` (023.4). Repos with `run_hook: false` are skipped with a printed note.
The docs repo is included (it is a normal workflow repo with the shared hook).

## Verification

- `git_commits_not_in_bare`: unit tests for (a) clean clone → 0, (b) two local commits on `main` → 2,
  (c) a brand-new branch with one commit → 1, (d) after push → 0.
- oob handoff integration test (real git repos in `tmp_path`, docker/tmux mocked): builder commits in
  `docs` and `dep1` only → `check` pushes exactly those two, prints both in the summary, leaves
  `mypackage` untouched; reviewer's clones are fetched but not checked out; a tracked modification in
  `dep1` fails the precondition; an untracked file only warns.
- `sync`: upstream repo advanced → `bare/<repo>`'s default branch moves to the new sha; a repo with
  only a `bare` remote is skipped; `--branch` pushes an extra branch; a repo with neither `main` nor
  `master` nor `origin/HEAD` fails with a clear message; `--dry-run` mutates nothing.
- In-band regression: the full `todo`→`implement`→`check`→`accept` round trip is byte-for-byte
  unchanged in behaviour (the push set reduces to the single repo).
- `black`, `ruff`, `pytest`, `mypy --strict` green.

## Risks

1. **`--remotes=bare` requires a fresh fetch.** A stale fetch under-counts and silently skips a repo
   that has commits to push. Every call site must fetch first; make that an explicit step in the
   resume plan rather than an implicit precondition.
2. **The forced push in `sync`** is the one destructive git operation added by this series. It targets
   only the resolved default branch of `bare/<repo>`; a code-repo feature branch pushed by an agent
   that happens to be named like upstream's default branch would be overwritten. Print the old and
   new sha and refuse when the fast-forward is not clean unless `--force` is passed.
3. **Third-party repos with unusual default branches** (`master`, `develop`, detached `origin/HEAD`)
   are the normal case for oob mode; the resolution order must be tested, not assumed.
4. **Hook fan-out cost.** Running N repos' hooks on every `check` may be slow; measure and, if it
   hurts, restrict to the push set (already the design) rather than adding a skip flag.
