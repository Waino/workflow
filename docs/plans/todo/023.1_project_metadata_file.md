# 023.1: Project metadata file (`.workflow.json`)

Input: `intent/023_out_of_band`
Completeness: complete

## Goal

Out-of-band (oob) mode needs a persistent, project-level record of the mode and (later) the list of
code repos. The current project-root indicator is an empty `.workflow_root` marker file, which can
hold nothing. Replace it with a single tool-owned JSON state file, `.workflow.json`, and make every
project-root lookup go through it.

This is the foundation for the rest of the 023 series: nothing else can branch on the mode until the
mode is stored somewhere.

## Scope

In scope:
- New `workflow/metadata.py`: `ProjectMetadata` pydantic model, atomic read/write.
- `find_project_root` looks for `.workflow.json`; `.workflow_root` is a hard error with migration
  instructions (no fallback).
- `WorkflowConfig` gains a runtime-populated `metadata` field, alongside `project_dir`.
- `init` writes `.workflow.json` (always `mode: in_band` at this stage).
- `doctor` reports a leftover `.workflow_root`.
- New `scripts/migrate_023.py` — single-use, idempotent migration script, grown by later plans in
  this series.
- User docs: the config-vs-state rule.

Out of scope: the `--oob` flag, code repos, mode immutability enforcement (all in 023.4); any path
resolution change (023.2).

## Design

### `workflow/metadata.py`

```python
METADATA_FILENAME = ".workflow.json"
LEGACY_ROOT_MARKER = ".workflow_root"

class ProjectMode(StrEnum):
    in_band = "in_band"
    oob = "oob"

class CodeRepoMeta(BaseModel):
    name: str
    run_hook: bool = True

class ProjectMetadata(BaseModel):
    version: Literal[1] = 1
    mode: ProjectMode = ProjectMode.in_band
    code_repos: list[CodeRepoMeta] = []
```

`version` is present from the start so a future schema change can be detected rather than
mis-parsed. `code_repos` stays empty in this plan; 023.4 populates it and adds the
"non-empty iff oob" validator (keeping the validator out of this plan avoids writing a rule the
`--oob` flag cannot yet satisfy).

Functions:
- `read_metadata(project_dir) -> ProjectMetadata` — raises `WorkflowError` on missing file, invalid
  JSON, or unknown `version`. Messages name the file path.
- `write_metadata(project_dir, metadata) -> None` — atomic: `tempfile.NamedTemporaryFile` in
  *the same directory* (so `os.replace` stays on one filesystem), `json.dump(metadata.model_dump(mode="json"), indent=2)`,
  then `os.replace`. On any exception the temp file is removed and the existing file is untouched.

Keep both functions free of console output so they stay unit-testable.

### Root discovery (`workflow/config.py`)

- Replace `WORKFLOW_ROOT_MARKER` with an import of `METADATA_FILENAME`.
- `find_project_root` matches on `.workflow.json`.
- Add `find_legacy_project_root` (same walk, matching `LEGACY_ROOT_MARKER`). `load_config` calls it
  only when `find_project_root` returned `None`, and then raises:

  > `{dir}` contains a legacy `.workflow_root` marker but no `.workflow.json`.
  > Run `python scripts/migrate_023.py --project-dir {dir}` to migrate.

  This is detection, not compatibility: no code path reads the legacy marker for its meaning.
- `WorkflowConfig` gains `metadata: ProjectMetadata | None = None`, populated by `load_config`
  exactly like `project_dir`/`project_name` (`None` when outside a project). Update the class
  docstring, which currently names `.workflow_root`.
- `init` runs outside an initialised project, so it must tolerate `metadata is None` and construct a
  default `ProjectMetadata()` itself.

### `init`

`_classify_marker_step` / `_STEP_MARKER` become the `.workflow.json` step: `satisfied` when the file
exists and parses, `will_run` otherwise. The run branch calls `write_metadata(project_dir, ProjectMetadata())`
instead of `Path.touch()`. Rename the step string to `"project metadata"`.

Note `_check_init_preconditions` must not require the metadata file (init is what creates it).

### `doctor`

Add one anomaly to the existing project-level checks (next to `_duplicate_plan_anomalies`): if
`project_dir / LEGACY_ROOT_MARKER` exists, report `"legacy .workflow_root marker present; run scripts/migrate_023.py"`.
This is how existing projects find out they were half-migrated.

### `scripts/migrate_023.py`

Single-use migration for pre-023 projects, created here and extended by 023.2/023.3/023.4. Prefer
this over any backwards-compatibility code in the package.

- `--project-dir DIR` (required), `--dry-run`.
- Step 1 (this plan): if `.workflow.json` is absent, write a default `ProjectMetadata()`; then delete
  `.workflow_root` if present.
- Idempotent: re-running is a no-op. Prints each action.
- Not part of the flit package (`scripts/` is outside `workflow/`), but is formatted by `black` and
  must pass `ruff`/`mypy` — extend the hook's `mypy` and `black` argument lists to include `scripts`.

## Documentation

Add a short subsection stating the rule, because the boundary will otherwise blur:

- `config.yaml` — hand-authored configuration; edited freely by the operator; resolved from CLI flag,
  project dir, or `~/.config/workflow/`.
- `.workflow.json` — tool-owned state; written only by `workflow` commands; never hand-edited;
  its presence marks the project root.

## Verification

- `tests/test_metadata.py`: round-trip write/read; unknown `version` rejected; malformed JSON gives a
  `WorkflowError` naming the path; `write_metadata` over an existing file leaves no `.tmp*` residue
  and preserves the old content when serialization raises (monkeypatch `json.dump` to raise).
- `tests/test_config.py`: `find_project_root` finds `.workflow.json` from a nested cwd; a project with
  only `.workflow_root` raises with the migration hint; `load_config` populates `config.metadata`.
- `tests/test_doctor.py`: legacy marker present → anomaly, exit 1.
- Integration: existing `init` tests assert `.workflow.json` exists and parses; resume test asserts
  the step is `satisfied` on a second run.
- Migration script: test in `tests/test_migrate_023.py` over a tmp project (old marker → new file,
  marker gone, re-run is a no-op).
- `black`, `ruff`, `pytest`, `mypy --strict` green.

## Risks

1. **Every test fixture that fakes a project root creates `.workflow_root`.** Expect a wide but
   mechanical test diff; missing one shows up as "not inside a workflow project directory".
2. **This repo is itself a pre-023 project.** After merging, the operator must run the migration
   script on the workflow project and on every other project. Post-completion task, flagged in the
   final summary.
3. **`load_config` raising on the legacy marker** turns a previously working project into a hard
   failure for *all* commands including `cheat`. That is intended (fail fast with a fix), but the
   message must contain the exact command to run.
