# 020.1: More robustness — PR fixes + remaining script commands

Input: `intent/020_robustness`, `done/020_robustness`, `reviews/pr/020_robustness_8582f69`
Completeness: complete — build in the phased commit order in "Build sequence".

## Goal

The 020 implementation landed the precondition/idempotent-resume vocabulary and applied
it to `init`, `start`, `check`, `accept`, `implement`, plus the new `doctor` command. The
PR review (commit 8582f69) found a merge-blocking `doctor` bug and two design smells that
risk reintroducing the original inconsistency class. It also left `todo`, `reject`, `push`,
`new`, and `go` untouched.

This plan (a) fixes the reviewer's findings and hardens against their recurrence, and (b)
extends the same robustness treatment to the five remaining script commands — with the
depth calibrated to each command's actual multi-step risk.

## Scope

In scope:
- **PR fixes:** doctor duplicate-detection bug (+ test gap), classify/execute drift,
  guarded/unguarded `transfer_branch_to_main` duplication, `check` resume running against
  `main`, `_transition_if_needed` staging assumption comment.
- **Rename:** `_prepare_agents_md_update` → `prepare_agents_md_update` (no longer private).
- **Remaining commands:** `todo` (full ResumePlan), `reject` (transition idempotence),
  and `push` / `new` / `go` (preconditions + cheap idempotence only).

Out of scope: any new command; changing the `--continue`/`--force` contract; the
`plan_resolver` same-command-rerun ambiguity recorded as a 020 deviation.

## Design decisions (locked)

Carried from 020 and refined here per the 2026-07-08 clarifications:

1. **Single source of truth for skip decisions.** The postcondition logic lives only in the
   `_classify_*` pass. Execution consults `resume.should_run(name)` rather than re-deriving
   conditions. See "Fix 2".
2. **One guarded `transfer_branch_to_main`.** The unguarded body and the inline copy in
   `implement` are replaced by a single idempotent, guarded helper used by `todo`,
   `implement`, and `accept`. See "Fix 3".
3. **Lightweight commands get preconditions + cheap idempotence, not the full two-pass
   preview.** `push`, `new`, `go` have no meaningful multi-step resume; forcing `ResumePlan`
   on a single mutating step adds ceremony without value.
4. **`new` always allocates the next number.** It is treated as non-resumable creation; the
   only new guard is refusing to overwrite an already-existing target path.

## Fixes to the 020 implementation

### Fix 1 — `doctor` flags intents/reviews as duplicates (high, merge-blocking)

`_duplicate_plan_anomalies` (workflow/commands/doctor.py) groups **all** plans from
`find_all_plans_in_repo`, so a plan legitimately co-existing with its originating `intent/`
file and/or its `reviews/pr` + `reviews/critique` documents is reported as "appears in
multiple state dirs" — exiting non-zero on every mature project.

Fix: before grouping, keep only pipeline states
(`PLANNING, TODO, IMPLEMENTING, CHECKING, DONE, REJECTED`) — exclude `INTENT` and any
`REVIEW`/review entries. Construct from `PlanState` by filtering out excluded states,
rather than enumerating positive states: this avoids drift if a new pipeline state is added to `PlanState`.
Define the pipeline-state set once (module constant) so it is not re-spelled.
`_active_feature_branches` already filters on `IMPLEMENTING/CHECKING` and is
unaffected.

Test gap (in `tests/test_doctor.py`): no case places an intent or review alongside a plan.
Add a case with a `reviews/pr/NNN_slug_hash.md` and an `intent/NNN_slug.md` present and
assert **no** duplicate anomaly is raised, plus keep a real botched-`git-mv` case (same
slug in two pipeline dirs) that still **is** flagged.

### Fix 2 — classification and execution are separate code paths (medium)

`ResumePlan.should_run` is unused in production; each `_run_*` re-derives the postconditions
the `_classify_*` pass already computed (init "wire canon to bare" and "AGENTS.md" run even
when classified `satisfied`; `implement` re-checks `plan.state`/`git_branch_exists`). This
duplicates the exact logic the plan calls "the whole ballgame" and lets the preview drift
from behavior.

Fix: drive each side-effect step off `resume.should_run(name)`:

```python
if resume.should_run("wire canon to bare"):
    _wire_canon_to_bare(...)
```

Apply to `init`, `check`, `accept`, `implement`, and the new `todo`. Step-name strings are
the join key between the two passes; keep them identical and centralize each command's names
as module-level constants so a rename can't silently break the join.

**Nuance — value-returning steps.** A transition must yield the updated `Plan` object even
when its `git mv` is skipped. Keep `_transition_if_needed` for those: gate the *call* on
`should_run` only where the return value is unused; where the caller needs `new_plan`, call
`_transition_if_needed` unconditionally (it is already idempotent and returns the correct
object pointing at the target dir). Document this split in a one-line comment so a future
reader does not "simplify" it into a skipped call that drops `new_plan`.

### Fix 3 — DRY `transfer_branch_to_main` (medium)

Today: `todo` calls the unguarded helper (with two hard assertions); `implement` inlines a
guarded copy that dropped the canon-on-`main` safety net (PR finding #3); `accept` open-codes
its own push/pull/merge. Collapse to one guarded helper in `git_helpers.py`:

```python
def transfer_branch_to_main(source_repo, canon_repo, *, branch=None, dry_run=False):
    require(git_current_branch(canon_repo) == "main",
            "transfer_branch_to_main: canon is not on 'main'; won't clobber a feature branch")
    merge_ref = f"origin/{branch or git_current_branch(source_repo)}"
    git_push(source_repo, dry_run=dry_run)          # pushes source's current branch
    git_pull(canon_repo, dry_run=dry_run)
    git_merge(canon_repo, merge_ref, dry_run=dry_run)   # "Already up to date" on re-run
    git_push(canon_repo, dry_run=dry_run)
    if git_current_branch(source_repo) != "main":       # idempotent checkout
        git_checkout(source_repo, "main", dry_run=dry_run)
    git_pull(source_repo, dry_run=dry_run)
```

Key changes vs. today:
- **Keep** the canon-on-`main` `require` (safety; resume-safe since canon is always on `main`
  at rest). This restores the guard `implement` had dropped.
- **Drop** the hard "source on `main`" failure. On a mid-transfer resume the source may
  already be on `main`; the idempotent ops then reduce to a harmless main→main merge. When
  the transfer genuinely should be skipped, the *classifier* marks it `satisfied` (below),
  so the helper is not called at all.
- **Add `branch=`** so `accept` merges the fixed `feat/{plan.name}` ref (decision 2 of 020)
  regardless of what reviewer is currently checked out to, while `todo`/`implement` pass
  `None` and use source's current branch.

Callers:
- `todo`: `transfer_branch_to_main(planner, canon)` — classified as one step
  `"transfer planner branch to main"`, `satisfied` when plan already past `planning`.
- `implement` (planning path): same call, replacing the inline block in `_run_implement_steps`.
- `accept`: `transfer_branch_to_main(reviewer, canon, branch=f"feat/{plan.name}")` as one
  step, then `_transition_if_needed(DONE)`, then `git_push(canon)`. This reorders reviewer→
  `main` to before the done-transition and adds one harmless extra canon push — accepted.

**Granularity note (reconciles Fix 2 and 020 decision 3).** 020's ambition was "each git op
is its own step". Per the 2026-07-08 direction favoring simplicity, the transfer is instead a
**single guarded+idempotent step**: its internal ops are each individually idempotent, so
re-running the whole unit is safe even when the classifier marked it `will_run` on a partial
prior run. This keeps classify- and run-granularity aligned (Fix 2) without an airtight
per-op framework.

Update `tests/test_git_helpers.py`: the "rejects main branch" test must change (source-on-
`main` is no longer a hard error); add a canon-not-on-`main` rejection test and an idempotent
re-run test (source already on `main` → no crash, no spurious checkout).

### Fix 4 — `check` resume runs pre-commit/validate against `main` (minor)

Steps 1–2 (`always` flavor) run before the transition check, so on a resume where a prior run
already advanced builder to `main`, the sandbox pre-commit hook + validate run against `main`.
Fix: only run pre-commit + validate when the plan has not yet transitioned, i.e. gate both on
`plan.state == PlanState.IMPLEMENTING` (when already `CHECKING`, the checks either already
passed or are moot because builder is on `main`). Add a comment stating why.

### Fix 5 — `_transition_if_needed` staging assumption (minor)

`_transition_if_needed` relies on `git_commit_if_changed`, which does not `git add -u`; a move
present only in the working tree (unstaged) would silently no-op the commit. Normal and
interrupted-after-`git mv` paths are pre-staged, so this is fine — add a one-line comment at
the call site noting the "rename must be pre-staged" assumption. No behavior change.

### Rename

`workflow/commands/agents_md.py`: rename `_prepare_agents_md_update` → `prepare_agents_md_update`
and update the single importer (`workflow/commands/workflow.py:18` and its call sites in
`_classify_agents_md_step`). Grep for any test references.

## Remaining commands

### `todo` — full ResumePlan (mirrors `implement`/`accept`)

Up-front preconditions: plan in `planning` (existing `_enforce_expected_state`); no index lock
in planner/canon; canon on `main`. (The dirty-planner check is the operator's responsibility;
`todo` runs validation already.)

| # | Step | Skip-if (postcondition) | Flavor |
|---|------|-------------------------|--------|
| 1 | `transfer_branch_to_main(planner, canon)` | plan already past `planning` | auto |
| 2 | transition plan → `todo` (mv + commit in canon) | plan file already in `todo/` | auto |
| 3 | push canon | bare `main` at canon `main` sha | auto (belt) |

Wire execution through `resume.should_run` (Fix 2). Validation runs before classification, as
in `check`. No `--continue` (all steps auto/always).

### `reject` — transition idempotence

`reject` already early-exits when the plan is `REJECTED`. Harden the rest:
- Precondition: no index lock in `target_repo`.
- Replace the raw `transition_plan` + `git_commit` with `_transition_if_needed(REJECTED, …)`
  so a resumed run (file already moved, commit missing) completes instead of failing.
- `git_push` after is naturally idempotent.

No ResumePlan preview (single transition step); the existing already-rejected short-circuit is
the "skip" path.

### `push` — preconditions + cheap idempotence

- Precondition: no index lock in the resolved repo.
- Keep the existing "on a feature branch, not `main`" guard.
- `git_push` (and the optional `pull_target` pull) are already idempotent; no further change.

### `new` — guard against overwrite only

- Keep `next_intent_number` auto-increment (decision 4): each run creates a fresh intent.
- Add a precondition: the computed `intent_path` must not already exist (fail fast rather than
  clobber). With auto-increment this should never trigger, so it is a cheap safety assertion.
- No other resume logic.

### `go` — preconditions only

Pure tmux rotation + read-only `git status`. No mutation, no resume. Leave as-is aside from
confirming it needs no lock/precondition additions (it does not touch git state).

## Risks

1. **Step-name string join (Fix 2).** `should_run` matches on the step name; a typo silently
   makes a step always run (or raises "no decision recorded"). Mitigate with per-command
   name constants shared by classify + run.
2. **`accept` reordering (Fix 3).** Routing through `transfer_branch_to_main` moves reviewer→
   `main` ahead of the done-transition and adds a redundant canon push. Verified inconsequential
   (transition is a canon-local `git mv`), but confirm the accept resume test still passes.
3. **Dropping the source-on-`main` hard fail (Fix 3).** A genuinely mis-invoked `todo` (planner
   accidentally on `main`) now silently merges main→main instead of erroring. Acceptable: the
   classifier's `satisfied`-when-past-`planning` gate is the real guard, and the outcome is a
   no-op, not corruption.
4. **`check` gating on `plan.state` (Fix 4).** If an operator wants to re-run validation after a
   transition, they must use `validate` directly. Note this in the comment.
