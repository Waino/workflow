# 004.4: Review fixes for CLI framework

Input: `docs/plans/reviews/pr/004_cli_framework_1e84d3a.md`

## Goal

Fix the functional gaps identified in the PR review for 004 so that the CLI is
actually usable: commands must exist at parse time, prompt templates must receive
the variables they need, plan resolution must target the correct repo for each
workflow stage, and the feature must gain thin CLI-boundary integration tests.

## Scope

- Replace callback-time command registration with a config-aware custom Click group
- Expose both script commands and prompt commands from config/registry
- Pass a `Plan` object to templates, with `plan.path` relative to the project dir
- Pass `branch` and `commit` to prompt templates
- Resolve plans using explicit repo hints derived from workflow stage
- Add thin integration tests around the CLI boundary with mocked git/tmux/editor deps

## Problem summary

The current branch has four concrete issues:

1. Commands are registered too late (inside the group callback), so Click cannot
   parse `ask`, `pr`, `todo`, etc.
2. Prompt rendering only passes `path_to_plan`, while the default `pr` template
   needs plan identity plus branch/commit metadata.
3. Plan resolution falls back to `master`, which is wrong for builder/reviewer
   flows and defeats the intended loose-path ergonomics.
4. The test suite does not exercise the CLI boundary, so the failures above were
   not caught.

## Design overview

### 1. Config-aware custom group (`workflow/cli.py`)

Use Option A from the follow-up discussion: replace the plain `click.Group` with a
custom `WorkflowGroup` that can load config before subcommand lookup.

Core shape:

```python
class WorkflowGroup(click.Group):
    def _get_runtime(self, ctx: click.Context) -> _CliRuntime: ...
    def list_commands(self, ctx: click.Context) -> list[str]: ...
    def get_command(self, ctx: click.Context, cmd_name: str) -> click.Command | None: ...
```

`_get_runtime()` will:

- read `ctx.params["config_path"]` and `ctx.params["dry_run"]`
- call `load_config(...)`
- cache the loaded config and generated command map on the current context
- return a small runtime object containing:
  - `config: WorkflowConfig`
  - `dry_run: bool`
  - `commands: dict[str, click.Command]`

The group callback remains, but becomes a light adapter that stores the already
loaded runtime into `ctx.obj` for command handlers. Do **not** mutate the command
table in the callback.

### 2. Unified dynamic command manifest

The custom group should build one command map from the config:

- prompt commands from `PromptCommand`
- script commands from `ScriptCommand` + `_SCRIPT_REGISTRY`

Add a helper that scans all states and de-duplicates by CLI name (kebab-case for
multi-word names). For repeated script commands like `doublecheck`, require that
the same CLI name always points to the same registered script name. If the config
ever maps one CLI name to multiple script targets, raise `ConfigError`.

Script command wrappers can stay minimal in this fix plan: they should expose the
currently configured zero-argument placeholder functions through Click without
expanding their argument model yet.

### 3. Keep `Plan.path` relative to the project directory

Change `workflow.models.Plan.path` semantics from absolute path to project-relative
path, e.g.:

- `Path("master/docs/plans/checking/004_cli_framework.md")`
- `Path("reviewer/docs/plans/reviews/pr/004_cli_framework_1e84d3a.md")`

This keeps prompts portable across host and sandbox environments while preserving
full information.

Add a helper on `Plan` for filesystem use:

```python
class Plan(BaseModel):
    path: Path  # relative to project_dir

    def absolute_path(self, project_dir: Path) -> Path:
        return (project_dir / self.path).resolve()
```

Update `plan_resolver.py` to always store relative paths:

- `find_all_plans_in_repo()` should use `md_file.relative_to(project_dir)`
- `_resolve_absolute()` should validate the absolute input, then return a `Plan`
  whose `path` is the relative path inside the project

Update model and resolver tests accordingly.

### 4. Prompt render context: `plan`, `branch`, `commit`

Stop passing `path_to_plan` / `plan_name` separately. Instead render with a small
explicit context:

```python
render_context = {
    "plan": plan,
    "branch": branch,
    "commit": commit,
}
```

This lets templates use:

- `{{ plan.path }}`
- `{{ plan.name }}`
- `{{ branch }}`
- `{{ commit }}`

Stateless review prompts continue to render without `plan`.

Update `docs/default_config.yaml` to use the new names. In particular:

- replace `{{ path_to_plan }}` with `{{ plan.path }}`
- replace `{{ plan_name }}` with `{{ plan.name }}` or `{{ branch }}` as appropriate
- change the PR template to use the explicit `branch` variable instead of asking
  the agent to derive it

### 5. Explicit repo hints by workflow stage

Do not derive repo paths from `agent_name`. Those are tmux targets; repo selection
is a workflow-stage concern.

Add a helper in `tmux_dispatch.py` that maps prompt commands to candidate workflow
targets. For each occurrence of a prompt command in config, record:

- the valid state(s)
- the repo name to search (`planner`, `builder`, `reviewer`)
- the tmux `agent_name` to send to

Examples:

- `ask` → planner repo for `intent`/`planning`, builder repo for `implementing`
- `build` → builder repo
- `pr` / `fix` → reviewer repo
- `full review` / `followthrough` → stateless review commands, no plan lookup

Resolution algorithm for plan-based prompts:

1. Build candidate targets for `cmd_name`
2. For each target, call `resolve_plan(..., expected_states=target.states, repo=target.repo_name)`
3. If exactly one target resolves, use it
4. If none resolve, print the most useful not-found error
5. If multiple resolve, raise/print a clear ambiguity error

This preserves loose path input while removing the incorrect implicit `master`
fallback for builder/reviewer commands.

### 6. Branch and commit metadata (`workflow/git_helpers.py`)

Add the lightweight read-only helpers already anticipated by plan 005:

```python
def git_current_branch(repo_path: Path) -> str: ...
def git_commit_hash(repo_path: Path, *, short: bool = True) -> str: ...
```

These should call `git rev-parse --abbrev-ref HEAD` and
`git rev-parse --short HEAD` (or full `HEAD`) respectively.

Prompt dispatch will use the resolved repo path to gather branch/commit before
rendering plan-based prompts.

Dry-run nuance: do **not** broaden dry-run into executing read-only git commands.
Instead, if dry-run is active, use obvious placeholders such as `<dry-run-branch>`
and `<dry-run-commit>` so prompt rendering still works without violating the dry-run
contract.

## File organization

- `workflow/cli.py` — `WorkflowGroup`, runtime/config caching, command lookup
- `workflow/tmux_dispatch.py` — prompt target discovery, repo-aware resolution,
  render context, prompt wrappers
- `workflow/git_helpers.py` — current branch / commit hash helpers
- `workflow/models.py` — relative-path semantics, optional `absolute_path()` helper
- `workflow/plan_resolver.py` — return relative paths
- `docs/default_config.yaml` — update templates to `plan` / `branch` / `commit`
- `tests/test_cli.py` — new thin integration tests
- `tests/test_plan_resolver.py`, `tests/test_models.py` — path semantics updates

## Dependencies

- Existing 004.1 / 004.2 / 004.3 implementation on this branch

- Planned 005 git helper direction for branch/hash lookup (implemented early here)

## Risks

- `click.Group.list_commands()` and `get_command()` must stay consistent; otherwise
  `--help` output and execution can diverge.
- Changing `Plan.path` semantics is cross-cutting. Keep the contract explicit in
  docstrings and update all affected tests in the same change.
- Commands like `ask` span multiple workflow stages/repos. The candidate-target
  resolver must prefer a unique match and produce a readable ambiguity message.
- Keep this fix plan scoped: do not expand script command argument parsing or add
  heavyweight end-to-end tmux tests yet.
