# 005.2: Doublecheck

Input: `intent/001_idea`, subdivided from `planning/005_plan_state_and_git`

## Goal

Implement the doublecheck verification suite as a reusable function and expose it
as a standalone CLI script command.

## Scope

- `doublecheck` function and `CheckResult` model
- Four individual verification checks
- Explicit target repo/actor override for callers such as `push`
- Config-driven git hook verification
- CLI registration as a script command

## Doublecheck function

Implemented as a reusable function, also exposed as a standalone CLI command.

```python
def doublecheck(
    plan: Plan,
    project_dir: Path,
    config: WorkflowConfig,
    *,
    target_repo_override: Literal["planner", "builder", "reviewer", "canon"] | None = None,
    dry_run: bool = False,
) -> list[CheckResult]:
    """Run all verification checks. Returns a list of results (pass/warn/fail)."""
```

- Start by fetching `origin` for the repo being checked (skipped in dry-run mode).
- When run as `workflow doublecheck`, infer the target repo from the plan state
  using `infer_target_repo(plan, target_repo_override)`.
  State → repo mapping:
  - `intent`, `planning` → `planner`
  - `todo`, `done`, `rejected` → `canon`
  - `implementing` → `builder`
  - `checking`, `review` → `reviewer`
- Callers such as `workflow push` may provide `target_repo_override` (now includes
  `"canon"` as a valid value) so doublecheck can inspect a different repo.
- Always print the target repo being used (done by the CLI command before calling this).
- In dry-run mode, return an empty list; the CLI prints a gray `[-]` placeholder for
  each check name instead of running real checks.
- Missing prerequisites are hard command errors, not `CheckResult`s.
  Examples: fetch failure, missing `.claude_md_hash`.

### CheckResult model

```python
class CheckResult(BaseModel):
    """Result of a single doublecheck verification."""
    check_name: str
    status: Literal["pass", "warn", "fail"]
    message: str
    details: list[str] = []  # e.g. list of noqa comments found
```

### Checks

1. **File scope verification** (`file-scope`): compare changed files on the branch against
   `origin/main` via `git diff --name-only origin/main...HEAD`.
   - `planner`: may modify `docs/plans/` (any state including intent) but NOT reviews or code.
   - `builder`: may modify code and `docs/plans/` (any state except intent and reviews).
   - `reviewer`: may modify everything EXCEPT `docs/plans/intent/`.
   - `canon`: no restrictions.
   Files not matching the allowed set are a failure; each violation is listed in `details`.

2. **Noqa/nosec listing** (`noqa-nosec`): list all `noqa` and `nosec` comments added in the
   branch diff (lines starting with `+` in `git diff origin/main...HEAD`).
   This is informational — status is `warn`, not `fail`.

3. **Git hooks verification** (`git-hooks`): `managed_hooks` in config maps hook filename
   to version-controlled source path (e.g. `{pre-commit: .git-pre-commit-hook}`).
   Each managed hook in `.git/hooks/` must be a symlink whose resolved path equals
   `{repo_root}/{hook_source}`. Any other executable non-sample file in `.git/hooks/` is
   a failure. Default config entry: `pre-commit: .git-pre-commit-hook`.

4. **CLAUDE.md integrity** (`claude-md`): verify that `CLAUDE.md` in the target repo hashes
   (SHA-256) to the trusted value stored in `{project_dir}/.claude_md_hash`. Also fail if the
   branch diff modifies `CLAUDE.md`. Hash file format follows `sha256sum` convention:
   `{hex_digest}  CLAUDE.md` (two spaces before filename). Missing hash file is a hard error.
   `workflow claude.md` is the command responsible for updating both `CLAUDE.md` and the trusted
   hash file. The trusted hash file lives once per project, outside the sandboxes, and is not
   version-controlled.

## CLI behavior

- `workflow doublecheck {path_to_plan} [--target-repo {planner|builder|reviewer|canon}]`
- Always prints: `Target repo: {target_repo}`
- **Dry-run mode**: print a gray `[-]` line for each check name; skip actual checks; return 0.
- **Normal mode**: print each `CheckResult` with a colored marker:
  - `[✓]` green for `pass`
  - `[!]` yellow for `warn`; details (noqa/nosec lines) are printed indented below
  - `[✗]` red for `fail`; details (violation list) are printed indented below
- Exit non-zero if any check returns `fail`.
- Only print the "next step is ..." reminder when all checks are non-failing:
  - `planning` state → `workflow todo {plan.name}` or `workflow reject {plan.name}`
  - `checking` state → `workflow accept {plan.name}` or `workflow reject {plan.name}`

## File organization

- `workflow/doublecheck.py` — `CheckResult`, `CHECK_NAMES`, `infer_target_repo`, `doublecheck`,
  and the four individual check functions
- `workflow/config.py` — `managed_hooks: dict[str, str]` field on `WorkflowConfig`
- `docs/default_config.yaml` — default `managed_hooks: {pre-commit: .git-pre-commit-hook}`
- `workflow/commands/workflow.py` — CLI command (`@register_script("doublecheck")` +
  Click decorators); `_build_script_command` in `cli.py` simplified to directly wrap the
  registered function with `click.command()` so Click decorators on the function are preserved

## Risks

- The file scope verification requires diffing branches, which assumes the branch exists
  and is based on `main`. Edge cases around rebases and force-pushes should be handled
  gracefully.
- Using a single trusted `.claude_md_hash` outside the sandboxes simplifies trust boundaries,
  but `workflow claude.md` becomes the only supported way to refresh it.
