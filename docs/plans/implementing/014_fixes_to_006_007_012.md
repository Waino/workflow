## Decisions

- **`also_valid_in_states` on `ScriptCommand`.** A new optional list of `PlanState`
  values that `_from_subcommand` adds to the states set in addition to the command's
  own state and `transition`. Keeps the "implement may be invoked from planning"
  rule in config rather than hard-coded in `plan_resolver.py`.
- **`pull_target` on `ScriptCommand`.** A new optional `RepoName` field. When set
  and not equal to the source repo, `push` runs `git_pull` in `pull_target` after
  `git_push` in the source repo. The reminder for the source command is printed
  afterwards. Matches the worked example "push from master to bare and pull in
  planner" in `intent/012_plan_resolution_respec.md`.
- **`push` main-branch guard.** Raise `WorkflowError` when the source repo's
  current branch is `main` *and* the source repo is not `master`. Master
  legitimately pushes `main` for intent/todo content; agent repos should always
  be on a feature branch when pushing.
- **`check` audit mapping.** Map `"check"` to `(RepoName.reviewer, PlanState.CHECKING)`
  in `AUDIT_COMMAND_REPO_STATE`. After `check` runs, the reviewer is the new owner.
- **`reject` transition.** Update `docs/default_config.yaml` so the `reject` entry
  reads `transition: rejected` (matching the script's hardcoded behaviour).
- **`accept` main guard.** Reuse the same wording as `transfer_branch_to_main`:
  raise `WorkflowError` when `git_current_branch(reviewer)` returns `"main"`.
- **`init` master-repo precheck.** Before the first `git clone --bare`, verify
  that `master/.git` exists and raise a `WorkflowError` with a clear message if
  not.
- **Slug validation for `new`.** Require
  `re.fullmatch(r"[a-z0-9]+(?:_[a-z0-9]+)*", slug)`; raise `WorkflowError` on
  mismatch.
- **`log --plan` fallback notice.** When `_resolve_plan_filter` falls back to
  substring matching, print one dim/yellow line on stderr before the table:
  `"Plan filter not uniquely resolved; falling back to substring match."`.
- **`implement` reminder sleep.** Bump `time.sleep(0.1)` to `time.sleep(1.0)`.
- **`_run_pre_commit_in_sandbox` quoting.** Use `shlex.quote(repo_path)` when
  building the `bash -lc` payload.
- **`git merge` flag-injection guard.** Update `git_helpers.git_merge` to use
  `["git", "merge", "--", branch]`.
- **Test-helper migration.** Replace the local `_noop`, `_return`, `_record_*`
  helpers in `tests/test_cli.py` and `tests/test_workflow_commands.py` with
  `unittest.mock.MagicMock` (and `mock.patch.object` where appropriate). Keep the
  scope of each test the same.
- **Integration test scope.** Exactly one happy-path integration test under
  `tests/test_integration_workflow.py`. Other commands (e.g. `reject`, `push`,
  `validate --target-repo`) stay on unit / `--dry-run` tests.

## Risks

- **Default-config schema change.** Adding `also_valid_in_states` and
  `pull_target` to `ScriptCommand` is backwards-compatible (both default to
  empty / `None`), but any user-supplied config that already uses those names
  for unrelated purposes will collide. Low risk since the config schema is
  internal.
- **`check` audit mapping change.** Changing `(builder, checking)` to
  `(reviewer, checking)` may invalidate stale audit log entries written by
  earlier versions on real projects. The resolver always picks the most
  recent matching entry, so a fresh `check` will overwrite the old one; only
  projects where `check` was the very last command and the user immediately
  upgraded would see different resolution behaviour. Acceptable.
- **Integration test flake on slow filesystems.** The end-to-end test uses
  real `git`. If git is missing or slow, the test should `pytest.skip`. Wall
  time is expected to stay under 2 seconds on a developer machine.
- **`shlex.quote` on `repo_path`.** Changing the docker payload string changes
  one existing assertion in `test_check_runs_pre_commit_and_prints_review_reminder`.
  The plan calls this out explicitly.
- **`git merge --` separator.** Some very old git versions (<1.7.10) do not
  accept `--` in `git merge`. The codebase already targets a recent git via
  the pre-commit hook; the risk is negligible.

## Phase 4a/4b/4c — Resolver corrections surfaced by the integration test

The first attempt at the Phase 4 integration test surfaced three further
resolver issues that block end-to-end `init → todo → implement → check →
accept`. They are tracked below as Phases 4a–4c so they can be committed
before the integration test itself (re-numbered Phase 4d).

### Issues

1. **Git data source contributes a misleading repo constraint.**
   `_from_git_history` returns the clone of the newest commit touching the
   plan file. After every transition commit (made in `master` and then pulled
   into the agent's clone), the file exists identically in both clones; git's
   tie-break on `%ct` arbitrarily picks one. For agent-owned states the
   resolver then sees `repos={master}` from git while `subcommand` correctly
   says `{builder}` / `{reviewer}` / etc. → empty intersection → failure.

2. **`AUDIT_COMMAND_REPO_STATE` is hand-maintained and disagrees with the
   config.** The constant in `workflow/audit.py` hardcodes `(repo, state)`
   pairs that the resolver consults for each audit-log entry. The current
   entries were filled in by hand and contradict the config — e.g. `implement`
   is mapped to `(master, implementing)` even though the config says
   `implementing` is owned by `builder`. The mapping must be derived from the
   config so the two cannot drift.

3. **Same-second commit timestamps in tests.** Git's `%ct` resolution is one
   second. Test commits performed in the same second tie. After (1) is fixed
   this only ever affects the *state* component of the git constraint, where
   ties produce the same answer (the file is in the same state in every
   clone). No code change needed; only a note.

### Decisions

- **D1: Git contributes state only, except for `push`.** `_from_git_history`
  gains a `provides_repo: bool` parameter (default `False`). The returned
  `_Constraint` carries `repos={…}` only when the caller opts in. The single
  opt-in callsite is the `push` script, whose entire purpose is to find the
  clone with manual edits that aren't in bare yet.

- **D2: Plumb the toggle through `resolve_plan`.** A new boolean
  `git_provides_repo` is added to `resolve_plan` (default `False`). The
  `push` callsite passes `git_provides_repo=True`. All other callsites
  (`todo`, `implement`, `validate`, `check`, `accept`, `reject`, `info`, and
  every tmux prompt dispatch) keep the default. See the table in §Sources
  below for the full justification.

- **D3: Derive `AUDIT_COMMAND_REPO_STATE` from the config.** A new helper
  `build_audit_command_repo_state(config) -> dict[str, tuple[RepoName,
  PlanState]]` walks `config.states`, finds every `ScriptCommand` *and*
  `PromptCommand` with a non-`None` `transition`, and records the
  `(agent_of_transition_state_or_master, transition)` pair. The hardcoded
  constant is removed; `_from_audit_log` accepts the mapping (computed once
  in `resolve_plan`) as a parameter.

- **D4: Keep behaviour for absent / non-transition commands.** Commands
  without a `transition` (e.g. generic `push`, `validate`, prompts such as
  `ask`/`critique`/`pr`/`fix`/`build`) contribute no audit constraint, just
  like today. Only transitions produce a mapping entry.

- **D5: `new` is a special case.** `new` is a `ScriptCommand` with no
  `transition` (it creates the intent file) but the current hardcoded
  mapping is `(master, intent)`. With D3 it would drop from the mapping. The
  resolver's existing fallback (silent source) is correct here: a freshly-
  `new`'d intent is uniquely identified by the filesystem and git anyway.
  The hardcoded entry was unnecessary; removing it is fine.

## Phase 4d — Integration test (revisited)

After 4a–4c, the integration test still fails at the `check` step. Root cause:
the resolver's audit-log source pins the state to the most recent transition
target (`implementing` after `implement`), while the *builder* agent — by
following the `build` prompt's instructions — moves the plan from
`implementing/` to `checking/` without producing an audit entry. The
subsequent `check` script then sees an empty state intersection
(`{implementing, checking}` from subcommand ∩ `{checking}` from git ∩
`{implementing}` from audit = ∅) and aborts.

### Issues

1. **Audit-log state constraint is too narrow.** Plans only ever move forward
   through the workflow (per 012 §Assumptions 1). The audit log captures only
   the transitions performed by *script* commands, but agent-driven moves
   (e.g. the builder running `git mv implementing/ → checking/` as part of
   `build`) are not logged. The audit's recorded state is therefore a *lower
   bound* on the plan's actual current state — not an exact value.

2. **`git commit --no-verify` is rejected by the sandbox git wrapper.** The
   integration test cannot use `wc.git_commit` as-is for transition commits.

3. **No file move in the simulated builder step.** Today's test only edits
   `README.md`; it omits the `git mv` that the `build` prompt instructs the
   builder agent to perform. The resolver correctly refuses to find a
   `checking`-state plan that doesn't exist on disk anywhere.

4. **`_from_git_history` tie-breaks by iteration order.** Phase 4a/b/c noted
   that same-second commit timestamps would only ever affect the *state*
   component "where ties produce the same answer". That assumption is
   wrong: after the builder's untracked `git mv implementing/ → checking/`,
   master's transition commit (`implementing`) and builder's move commit
   (`checking`) commonly share a `%ct`, and the resolver arbitrarily picks
   the first iterated repo's state. The integration test, with no sleep
   between steps, hits this every run.

### Decisions

- **D6: Audit log contributes forward-progression states.** `_from_audit_log`
  returns `states = {recorded_state} ∪ {all states ranked after it in
  _STATE_PROGRESSION}`. The repo dimension is unchanged (still
  `{recorded_repo}`). Rationale: the recorded state is a *lower bound* —
  anything ranked at or after it is consistent with the audit evidence. This
  matches the spec semantic "tickets only ever move forward" and removes the
  audit's false negatives without weakening it for the cases that already
  worked (every test in `TestAuditSource` and `TestAuditCheckMapping` still
  passes because the actual plan on disk lies in the kept subset).

- **D7: The integration test bypasses `--no-verify`.** Inside the test,
  `monkeypatch.setattr(wc, "git_commit", …)` substitutes a plain
  `git commit -m` so the sandbox accepts it. No production-code change.

- **D8: Simulate the builder's `git mv` in the test.** Step 6 of the test
  performs `git mv docs/plans/implementing/005_foo.md
  docs/plans/checking/005_foo.md` (and commits) before invoking `workflow
  check`. This mirrors what the `build` prompt instructs the builder agent
  to do.

- **D9: Break `_from_git_history` timestamp ties by state progression.**
  When two repos report the newest plan-touching commit at the same `%ct`,
  the more progressed state wins. Tickets only move forward (012
  §Assumptions 1), so the higher-ranked state is the actual current state.
  This avoids `time.sleep` in tests and makes the resolver deterministic
  under one-second timestamp granularity.
