# 005.2: Doublecheck

Input: `intent/001_idea`, subdivided from `planning/005_plan_state_and_git`

## Goal

Implement the doublecheck verification suite as a reusable function and expose it
as a standalone CLI script command.

## Scope

- `doublecheck` function and `CheckResult` model
- Four individual verification checks
- Explicit target repo/actor override for callers such as `push`
- Config-driven git hook verification
- CLI registration as a script command

## Doublecheck function

Implemented as a reusable function, also exposed as a standalone CLI command.

```python
def doublecheck(
    plan: Plan,
    project_dir: Path,
    config: WorkflowConfig,
    *,
    actor_override: Literal["planner", "builder", "reviewer"] | None = None,
) -> list[CheckResult]:
    """Run all verification checks. Returns a list of results (pass/warn/fail)."""
```

- Start by fetching `origin` for the repo being checked.
- When run as `workflow doublecheck`, infer the target repo from the plan state.
  This follows the normal owner of the state; for `checking`, that means reviewer.
- Callers such as `workflow push` may provide `actor_override` so doublecheck can
  inspect a different actor repo than the default state-based one.
- Missing prerequisites are hard command errors, not `CheckResult`s.
  Examples: fetch failure, missing branch, missing `origin/main`, missing `.claude_md_hash`.

### CheckResult model

```python
class CheckResult(BaseModel):
    """Result of a single doublecheck verification."""
    check_name: str
    status: Literal["pass", "warn", "fail"]
    message: str
    details: list[str] = []  # e.g. list of noqa comments found
```

### Checks

1. **File scope verification**: compare changed files on the branch against `origin/main`.
   - Planner may modify plans, but not reviews.
   - Builder may modify code and plans, but not intents or reviews.
     This includes the current implementation plan and other non-intent, non-review plans.
   - Reviewer may modify everything except intents.
2. **Noqa/nosec listing**: list all `noqa` and `nosec` comments added in the branch diff.
   This is informational (warning), not a failure.
3. **Git hooks verification**: the list of managed hooks comes from config rather than being
   hard-coded. Each managed hook in `.git/hooks/` must be a symlink to the corresponding
   version-controlled hook file in the repo root. Any other executable non-sample hook is a failure.
4. **CLAUDE.md integrity**: verify that `CLAUDE.md` in the checked repo hashes to the trusted
   value stored in `{project_dir}/.claude_md_hash`, and fail if the branch diff against
   `origin/main` modifies `CLAUDE.md`.
   `workflow claude.md` is the command responsible for updating both `CLAUDE.md` and the trusted
   hash file. The trusted hash file lives once per project, outside the sandboxes, and is not
   version-controlled.

## CLI behavior

- `workflow doublecheck {path_to_plan}` prints all results.
- Warnings are highlighted with a yellow `[!]` prefix and do not cause failure.
- Exit non-zero if any check returns `fail`.
- Only print the usual "next step is ..." reminder when all checks are non-failing.

## File organization

- `workflow/doublecheck.py` — `doublecheck` function, `CheckResult`, individual check functions
- `workflow/config.py` — config field for the managed hook names
- `docs/default_config.yaml` — default managed hook list

## Dependencies

- Plan 002 (models): `Plan`, `WorkflowConfig`
- Plan 004.1 (CLI and registry): `run_command`, dry-run support
- Plan 005.1 (git helpers): git diff helpers for branch comparison

## Risks

- The file scope verification requires diffing branches, which assumes the branch exists
  and is based on `main`. Edge cases around rebases and force-pushes should be handled
  gracefully.
- Using a single trusted `.claude_md_hash` outside the sandboxes simplifies trust boundaries,
  but `workflow claude.md` becomes the only supported way to refresh it.
