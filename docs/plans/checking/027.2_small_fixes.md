# 027.2: Small fixes (next step, dry-run, resume plan, stack display)

Input: `intent/027_various_fixes.md` (items 3, 4, 5, 6, 7, 9)
Completeness: complete

## Goal

A handful of unrelated rough edges:

- `status`'s next-step column is almost always empty, because it tries to re-derive the next step
  from the audit log after the fact.
- `workflow agents_md` writes files under `--dry-run`.
- The resume plan prints twice, is titled "Resume plan" even on a fresh run, and dry-run output
  doesn't say where commands run.
- `doctor` reports false stack anomalies for accepted subdivided plans, due to a real resolver bug.
- The `stack` column is too wide.

## 1. Next step recorded in the audit log (item 3)

### Model and helper

- `AuditLogEntry.next_step: str | None = None`, documented as display text that must never be
  parsed.
- Replace `find_reminder_name`, `find_next_step`, `format_next_step_invocation` and
  `find_source_state_for_command` in `workflow/next_step.py` with one function:
  `format_next_step(config, command: Command, plan_name: str) -> str | None`.
  - The reminder is the command's `reminder`. There is no implicit fallback to the first command
    of the transition target state.
  - If the reminder names a non-manual command (via `find_step_by_name`), return
    `workflow <cli-name> <plan_name>`. Otherwise return it verbatim (free text such as
    `accept or reject`, `git commit, then workflow push`, manual steps).
  - Keep `find_command` (used by `push`) and `find_step_by_name`. Delete the rest.
    `find_source_state_for_command` is only used by `status`.

### Explicit reminders (`docs/default_config.yaml`)

Default = the next command in the state's list, adjusted where that's wrong:

| state | command | reminder |
|---|---|---|
| intent | architecture | mvp |
| intent | mvp | critique |
| intent | ask | answer |
| intent | critique | plan or subdivide |
| intent | subdivide | critique |
| planning | critique | todo |
| planning | todo | implement |
| planning | validate *(new entry, see below)* | todo or reject |
| implementing | ask | build |
| checking | fix | validate (unchanged) |
| checking | validate | accept or reject |

Existing reminders stay unchanged. `accept`, `reject`, the todo-state `push` and the review-state
prompts get none.

`validate` is added as a script command to the `planning` state: `rebase` there already points to
it, and `_print_validate_next_step` handles planning. This also lists it in the planner's
cheatsheet and AGENTS.md section.

### Writers

- `_print_command_reminder` in `workflow/commands/workflow.py` becomes a helper that returns the
  text and prints it. The six callers (new, todo, implement, check, push, accept) pass the text to
  `_write_script_audit_log(next_step=...)`.
  - Reorder where needed so the text is computed before the audit write.
  - Add a `next_step` keyword to `_write_script_audit_log`.
- `validate`:
  - Delete `_print_validate_next_step`.
  - On success only (not dry-run, no failures), compute the text from
    `find_command(config, plan.state, "validate")`, print it, and write an audit entry
    (`command="validate"`, `input_plan=plan.name`, `next_step`).
  - If the command isn't defined in the plan's state, write the entry without a next step.
- Prompt dispatch (`_dispatch_prompt`): after a successful send, compute the text from the
  definition actually used; borrowed prompts record none (see 027.1 §3). Print `Next step: …` and record
  it on the audit entry. Stateless (review) prompts use `plan_name=""` and have no reminder anyway.

### Reader (`status`, `workflow/commands/info.py`)

- The `next step` cell shows `last_entry.next_step` with the `workflow ` prefix and
  ` {last_entry.input_plan}` removed (plain `str.replace`, applied only when `input_plan` is set).
  Nothing else.
- Entries without `next_step` show an empty cell.
- The column loses its rich command styling. That's acceptable.

## 5. False stack anomalies (item 6)

Root cause, replicated in a throwaway test with dotted plan names:

- `_name_matches_seq` in `workflow/plan_resolver.py` uses `Path(plan_name).stem`, which turns
  `023.1_project_metadata_file` into `023`. The audit source is therefore silent for every
  subdivided plan.
- Without it, a done plan present in several worktrees matches more than once, and
  `resolve_plan` raises `AmbiguousPlanError`.
- The same replication showed `implement 005.1_foo` right after `todo` failing as ambiguous when
  the tmux source is silent.

Fix:
- Add one helper that strips only a trailing `.md` and any directory part, e.g.
  `plan_name.rsplit("/", 1)[-1].removesuffix(".md")`.
- Use it in both `_name_matches_seq` and `_top_level_number_from_name` (same `.stem` bug).
- In `_stack_anomalies` (`workflow/commands/doctor.py`), check `onto` with
  `find_stack_member(layout, fm.onto)` instead of `resolve_plan`. `onto` is an exact name, and
  `find_stack_member` isn't state-filtered.
- Drop the now-unused imports.

## Risks

- Removing the implicit reminder fallback changes behaviour for project configs that relied on it
  (e.g. `todo` → `implement`). The default config gets explicit reminders; document the change.
- Free-text choice reminders print `Next step: accept or reject` without the plan name. That's
  slightly less copy-pasteable than today's hardcoded validate line, accepted for a single mechanism.
- The dry-run safety test is the heaviest new test. Keep the fixture shared (module-scoped) if the
  runtime becomes noticeable, but each command must start from an identical snapshot.
- `status` strips text with `str.replace`. Harmless for display, but it's the only place touching
  `next_step`'s content: nothing else may.
