# 023.6: validate, doctor, `info` matrix and plan frontmatter

Input: `intent/023_out_of_band`, `planning/023.5_multi_repo_git_orchestration`
Completeness: complete

## Goal

Restore the safety net for oob mode. `validate`'s three interesting checks (file scope, git hooks,
AGENTS.md integrity) all assume one repo per worktree with plans at `docs/plans/**` and a committed
`AGENTS.md`; in oob mode each of those assumptions is false, so without this plan `validate` either
passes vacuously or fails always. Same for `doctor`. Finally, with up to four repos per worktree the
operator needs a status matrix instead of a linear list.

## Scope

In scope: per-repo `validate`, plan `branches` frontmatter (parser + presence check + generated
documentation), doctor's oob checks, the `info` matrix, and mode-parameterised test fixtures.

Out of scope: nothing further in the 023 series; this is the last plan.

## Design

### `validate` becomes per-repo

`validate()` currently diffs one repo (`project_dir / target_repo`) and returns four `CheckResult`s.
In oob mode it iterates `layout.repos()` in the acting worktree:

- `CheckResult` gains `repo: str | None` (rendered as a column; `None` for worktree-level checks).
- `git fetch bare` + `git diff bare/main...HEAD` per repo — except code repos, where `bare/main` is
  meaningless: diff against the merge base with the repo's *bare-known* base
  (`git diff $(git merge-base HEAD @{u} || echo HEAD)...HEAD`). Simpler and sufficient: for code
  repos use `git log --name-only HEAD --not --remotes=bare` to enumerate changed files, reusing the
  023.5 ahead-of-bare notion instead of inventing a second baseline.

Per-check behaviour in oob:

| check | oob behaviour |
|---|---|
| `file-scope` | docs repo: the current rules with `plans_prefix` (`plans/**`), plus `body_of_agents.md`/`bootstrap_venv.sh` allowed for `planner`/`canon` and **rejected** for `builder`/`reviewer` (they must not edit their own instructions or the script that builds their env). Code repos: unrestricted for `builder`/`reviewer`. |
| `planner-code-commits` (new) | fails when the `planner` worktree has commits not in bare in any code repo (the planner explores and checks out, but never commits code). |
| `noqa-nosec` | unchanged, run over the concatenated diffs of all repos. |
| `git-hooks` | per repo; skipped for repos with `run_hook: false`; for code repos an unexpected executable hook is a **warning**, not a failure (husky, pre-commit framework); for the docs repo the current strict rules apply. |
| `agents-md` | verifies the hash file against the AGENTS.md at **each** worktree root (all four must match, catching a drifted copy). The "modified on this branch" arm applies only in in-band mode; in oob the equivalent is `file-scope` rejecting `body_of_agents.md` for builder/reviewer. |
| `branches-frontmatter` (new, oob only) | see below. |

`CHECK_NAMES` is the single source of truth for the check list; add the two new names there.

### Plan `branches` frontmatter (decision 6)

Optional YAML frontmatter at the top of a plan file:

```yaml
---
branches:
  mypackage:
    branch: feature/widget-cache
    base: origin/main
  dep1:
    branch: fix/leak
    base: 7f3a91c
  dep2: null
---
```

`workflow/frontmatter.py` already exists as of plan 025 (stacked plans), which introduced
`parse_frontmatter`/`render_frontmatter`/`strip_frontmatter`/`write_frontmatter`, `RepoBranch`
(`branch: str; base: str`), and `PlanFrontmatter` with `extra="allow"`, an `onto: str | None` key and
`branches: dict[str, RepoBranch]` keyed by repo name (`DOCS_REPO` only, in in-band mode).
This plan extends that module rather than creating it:
- widen `branches` to `dict[str, RepoBranch | None]` so an unused code repo can be `null`;
- keep `onto` untouched — it is orthogonal to the oob branch bookkeeping.

The `branches-frontmatter` check (oob only, and only for plans in `implementing`/`checking`):
frontmatter exists, contains `branches`, has an entry for every code repo in `.workflow.json`, and
each non-null `branch` passes `git check-ref-format --branch NAME` (delegating name validity to git
rather than a hand-rolled regex). Nothing else is validated — no existence check on branches or
bases, per decision 14.

So that agents know to write the block, `render_workflow_section` gains the mode and, in oob mode,
emits a short paragraph documenting the required frontmatter and the repo list. This keeps the
requirement out of the mode-agnostic prompt texts in `config.yaml` and makes it appear only where it
applies. `WorkflowConfig`/the template gain `metadata`/`mode` inputs; the hash file already covers
`config.yaml`, so add `.workflow.json` to the hashed inputs (its `code_repos` now affect the output).

### `doctor`

Add, for oob projects:
1. every worktree × repo clone exists, is valid, and has **exactly one** remote, named `bare`
   (decision 16 — the load-bearing guarantee that agents cannot reach upstream);
2. all four worktree-root `AGENTS.md` copies exist and hash-match `.agents_md_hash`;
3. tracked-dirty repos reported per repo (untracked as a note, mirroring 023.5's precondition);
4. the bare-staleness note from 023.5.

`WorktreeCheck` grows a `repo` field and the table a `repo` column; in in-band mode the column is
omitted so today's output is unchanged.

### `info` matrix (decision 15)

In oob mode, replace the linear per-worktree `git_status` output with a matrix: rows = worktrees,
columns = repos, cell = `branch` + ahead/behind-bare counts + `*` when tracked-dirty. In-band output
is unchanged. Reuse the git helpers from 023.5 rather than shelling out again.

### Test fixtures (decision 19)

Add a `make_project(tmp_path, *, mode, code_repos=())` factory to `tests/conftest.py` that builds real
git repos, writes `.workflow.json`, and returns a `Layout`. Parameterise over both modes:
`test_plan_resolver.py`, `test_state.py` (transitions), `test_validate.py`, `test_doctor.py`. Leave
the wide resolver test in-band only (its value is resolver breadth, not layout).

## Verification

- `tests/test_frontmatter.py`: no frontmatter → `None`; valid block round-trips; `dep2: null` parses as
  `None`; malformed YAML raises naming the plan; unknown top-level keys are preserved.
- `validate` oob tests: planner branch touching only `plans/**` passes; planner with a commit in
  `dep1` fails `planner-code-commits`; builder editing `body_of_agents.md` fails `file-scope`;
  builder editing arbitrary files in `mypackage` passes; a code repo with a stray executable hook
  warns while the docs repo with one fails; a drifted `AGENTS.md` copy in `reviewer` fails
  `agents-md`; a plan in `implementing` without a `branches` block fails, and with one for every code
  repo passes.
- In-band regression: `validate` returns exactly today's four results with identical statuses.
- `doctor` oob tests: an agent code repo with an extra remote → anomaly; a missing clone → anomaly; a
  clean project → exit 0.
- `info` oob test asserts one row per worktree and one column per repo; in-band output unchanged.
- `black`, `ruff`, `pytest`, `mypy --strict` green.

## Risks

1. **The code-repo diff baseline** is the subtlest part of this plan. `bare/main` does not exist for
   third-party repos; using "commits not in any bare ref" keeps one definition shared with 023.5's
   push set, but it means `validate` reports on *all* unpushed commits rather than a branch diff.
   That is the correct scope for review, but it differs from in-band semantics — document it.
2. **`file-scope` for code repos is unrestricted**, so the only thing standing between the builder and
   an unwanted change in `dep2` is the plan's frontmatter and the human review. Accepted: oob mode
   exists precisely to work in repos whose layout the tool cannot know.
3. **Adding `.workflow.json` to the AGENTS.md hash inputs** means `add-repo` invalidates AGENTS.md and
   the operator must re-run `workflow agents_md`. Make the mismatch message say so explicitly, as the
   `config.yaml` arm already does.
4. **Four AGENTS.md copies** make drift detection essential; if the doctor check is weakened or
   skipped, agents can end up with different instructions and no signal.

## Clarifications (builder Q&A, pre-implementation)

1. **Doctor's new "exactly one remote, named bare" check applies to planner/builder/reviewer
   worktrees only, never canon.** Canon's code repos deliberately keep their own `origin` remote
   alongside `bare` (023.5, for `workflow sync`); the "agents cannot reach upstream" guarantee only
   needs to hold in the three agent worktrees.
2. **The AGENTS.md hash file bumps to a `v2` format**: `v2 <agents_md_sha> <config_yaml_sha>
   <workflow_json_sha>` (4 whitespace-separated tokens). Old `v1` files simply fail to parse as `v2`
   and are treated as a legitimate hash mismatch (same message path as any other mismatch, pointing at
   `workflow agents_md`); `parse_hash_file`/`HashFileV1` become `HashFileV2` (or gain a discriminated
   union if a reason emerges to keep reading old files, which none does here — `agents_md` regenerates
   the whole file unconditionally).
3. **`planner-code-commits` is a fixed, always-on check** in oob mode: it always inspects the
   `planner` worktree's code repos for commits not in bare, regardless of which worktree/plan is
   actually being validated in that call. It is not gated on `target_worktree == planner`.
4. **Code repos' full diff text (for `noqa-nosec`)** comes from `git log -p HEAD --not
   --remotes=bare` — the patch-concatenated counterpart to the `--name-only` file list and to
   `git_commits_not_in_bare`'s commit count, so all three read one consistent "reviewable diff"
   definition for a code repo (see Risk 1).
5. **The tracked-vs-untracked dirty-tree split applies uniformly**, everywhere doctor checks a
   working tree (docs and code repos, in-band and oob alike): tracked changes are an anomaly,
   untracked-only is a note. This is a (minor, documented) behaviour change for in-band/docs-repo
   dirty detection, not just a new rule for code repos.
6. **`CHECK_NAMES` is split into a mode-aware check list** rather than one flat list validate()
   filters internally: e.g. `CHECK_NAMES_IN_BAND` (today's four) and the two additional oob-only names
   (`planner-code-commits`, `branches-frontmatter`), combined into whatever list applies for a given
   mode. Both `check`'s dry-run preview and `validate()` itself consult the mode-appropriate list, so
   dry-run's static preview (run before any repo is touched) shows exactly the checks that would run,
   and in-band `validate()` keeps returning exactly today's four `CheckResult`s.
7. **Doctor's bare pseudo-worktree gets one row per repo** in oob mode (`bare`/`docs`,
   `bare`/`mypackage`, `bare`/`dep1`, ...), matching the one-row-per-(worktree, repo) shape the rest of
   the table gains; bare's existing checks (valid, index-lock) run once per repo directory under
   `bare/`.
8. **`tests/conftest.py`'s new `make_project` factory is filesystem-only** (writes `.workflow.json`
   and returns a `Layout`; no real git repos) — the same tier as the existing `make_layout`, just
   parameterised over mode/code_repos. It is for tests whose value is path math / plan resolution
   (`test_plan_resolver.py`, `test_state.py`), not git behaviour. Tests that need real git repos (most
   of `test_validate.py`'s and `test_doctor.py`'s new oob cases) keep using the heavier `_git`/`_init_repo`-style
   helpers already established in `tests/test_init_oob.py`.
