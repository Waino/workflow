## 027.1 Prompt dispatch

Spec coverage: `Plan.worktree`/`path_in_worktree`, routing by worktree with same-state preference, removal of
the `targets[0]` fallback, borrowing rules, the canon error, the `rebase` YAML anchor plus the builder entry,
`Plan resolved to:`, the blind suffix and extra delay, the `send_prompt_to_agent` docstring fix, the doctor audit
section, and the docs are all present. The stack-tip check now uses `plan.state`, as the plan requires.

### Medium

1. **Borrowed prompts record the lender's reminder as the next step.** The borrowed target is a copy of
   `definitions[0]`, so `format_next_step(config, target.command, …)` uses that definition's `reminder`.
   I confirmed this in a scratch project:
   - `critique builder/…/implementing/028_new --edit` prints and logs `Next step: plan or subdivide`.
   - `build reviewer/…/checking/028_new --edit` prints and logs `Next step: workflow check 028_new`, which is
     not a valid command for a checking plan.

   The value is written to the audit log and then shown by `status`, so a one-off borrow leaves a misleading
   next step on the plan until another logged command runs. 027.2 §1 says "including borrowed ones", so this
   follows the plan to the letter, but the result is wrong. Suggested fix: record no next step for a borrowed
   prompt (`next_step=None` when `resolved.borrowed`). The borrow is ad hoc by definition, so the lender's
   workflow position doesn't apply.
2. **Doctor's "unknown command" anomaly can never be cleared.** The audit log is append-only. If a user renames
   or removes a command from their `config.yaml` (e.g. drops `architecture`), every historical entry for it
   is flagged, and `doctor` exits 1 from then on. There's no way to acknowledge or repair it short of editing
   the log by hand. The intent's goal is to catch entries that corrupt the resolver's audit source, and only
   the transition-actor mismatch does that. Unknown commands are silently ignored by
   `build_audit_command_repo_state`. Suggestions: report unknown commands in the non-failing *notes* column
   (or a non-failing section), and keep only the transition-actor check as an exit-1 anomaly. A smaller point:
   `transition_agents` can contain `None` (a transition prompt in a state with `agent: null`), and then every
   entry for that command is flagged.

### Low

3. `blind = active_tmux_repo(...) != WorktreeName(agent_name)`:
   - `WorktreeName(agent_name)` raises a bare `ValueError` (traceback) if a custom config uses an agent name
     that isn't a worktree name. `result.worktree_name` already holds the recipient worktree, so compare
     against that and the conversion goes away.
   - `blind` is computed before `git_pull`, `refresh_main`, the code-repo fetch and, above all, before the
     `--edit` editor session. After a long edit the user may be on a different window, so both the warning and
     the extra delay are decided on stale state. Computing it just before `send_prompt_to_agent` costs nothing.
4. `docs/source/cli.rst` says "Every dispatch prints `Plan resolved to: <path>` and the recipient". Stateless
   prompts (`full-review`, …) don't print the plan line. Suggested wording: "Every plan dispatch prints…".
5. Test gaps:
   - `test_rebase_routes_to_builder_using_the_implementing_definition` only asserts the recipient. The three
     `rebase` prompts share their text, so the test would still pass if the planning definition were picked.
     Assert the next step instead (`workflow check …`, which only the implementing entry yields).
   - Nothing verifies that a borrowed target reads `{{ branch }}`/commit from the recipient's worktree (the
     core of the §3 `model_copy` rule). Dry-run returns placeholders. A non-dry-run test with
     `git_current_branch` patched to record its `repo_path` would cover it.
   - `test_real_send_sleeps_twice_only_when_blind` doesn't assert the `Sending to '…'` line or its suffix.
6. The new pydantic fields `_ResolvedTarget.*`, `_PromptContext.plan_path` and `_PromptContext.next_step` have
   no field docstrings. The project convention asks for them.

## 027.2 Small fixes

Spec coverage: `AuditLogEntry.next_step`, a single `format_next_step`, the obsolete helpers deleted, explicit
reminders, `validate` in `planning`, the writers reordered, the `validate` audit entry written on success only,
the prompt next step, the `status` reader and stack cell, `agents_md --dry-run`, `ResumePlan` titles and the
single render, `would run in <cwd>`, the `.stem` fix in both parsers, `_stack_anomalies` using
`find_stack_member`, the dry-run safety test, and the docs are all present. All `abort_unless_continue` callers
render first (checked at every call site).

### Medium

7. **`status` mangles free-text next steps.** `_display_next_step` does `next_step.replace("workflow ", "")`
   on the whole string, not just the prefix. The default `new` reminder `git commit, then workflow push`
   therefore shows as `git commit, then push`, which reads as `git push`: the wrong command. Use
   `removeprefix("workflow ")`, which matches the plan's "the `workflow ` prefix … removed", and add the `new`
   reminder as a parametrized case in `test_display_next_step`.
8. **The dry-run safety test is partly vacuous.** Exit codes are deliberately not asserted. My probe of the
   same sandbox shows that 5 of the 20 commands refuse before reaching any mutating code:

   | argv | outcome |
   |---|---|
   | `add-repo extra`, `sync` | "only valid for out-of-band projects" |
   | `implement 006_planning` | builder is on `feat/005_implementing` with unfinished work (needs `--onto`) |
   | `init` | clones exist, so it needs `--continue` |
   | `push 006_planning` | "Sources disagree" (push isn't defined for planning plans) |

   `implement` and `init` are among the most side-effect-heavy commands, so the test gives false confidence
   exactly where it matters. Suggestions:
   - Assert `exit_code == 0` except for an explicit, commented set of expected refusals.
   - Change the argv so the commands proceed: `implement 006_planning --onto 005_implementing`,
     `init --continue`, and `push` on an intent plan.
   - Add an oob sandbox, or an oob variant of the fixture, for `add-repo` and `sync`.

   The snapshot also has two gaps:
   - `git symbolic-ref -q HEAD` prints nothing on a detached HEAD, so a dry-run that detaches or moves a
     detached HEAD goes unnoticed. Add `git rev-parse HEAD`.
   - Only `refs/heads` and `refs/tags` are compared. That's a fine choice for remotes, but refs such as
     `refs/stash` are missed. Comparing `for-each-ref` output minus `refs/remotes/` would be stricter at the
     same cost.

### Low

9. The `status` stack cell calls `find_stack_member(layout, fm.onto)` with the default canon preference. For a
   planning plan whose base exists only on the planner's `plan/*` branch, it falls back to the full `onto`
   name, so the column widens again. Passing `prefer_repo=plan.worktree` fixes that. Doctor scans canon only,
   so its canon default is consistent there.
10. `_display_cwd` uses `Path(cwd).absolute()` but compares it against `Path.cwd()`, which is symlink-resolved.
    When the project is reached through a symlink (e.g. macOS `/tmp` → `/private/tmp`, or a symlinked home),
    every line falls back to an absolute path. Using `resolve()` on both sides avoids that.
11. The `reminder` fields in `workflow/config.py` still have no docstring. Their semantics are now load-bearing
    (a command name gets rendered as `workflow <cmd> <plan>`, anything else is shown verbatim) and there's no
    config reference in the user docs. The `cli.rst` wording "is no longer inferred" is changelog phrasing;
    describe the current behaviour instead.
12. The plan asked to verify that "the abort path prints the plan once". `test_steps` only checks that
    `abort_unless_continue` prints nothing. No command-level test asserts a single `Resume plan` block for a
    `NEEDS_CONTINUE` run (e.g. `init` without `--continue`, which the sandbox above already produces).
