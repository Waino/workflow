## 023.5 — Multi-repo git orchestration

### Spec coverage

Implemented: `git_commits_not_in_bare`, `git_status_porcelain(untracked=)`, `git_fetch_remote`,
`git_push_refspec`, `resolve_upstream_default_branch`, the push set in `check`/`accept`, per-repo hook
fan-out, dirty preconditions, fetching code repos in `_sync_repos_best_effort` and in `tmux_dispatch`,
`workflow sync` with fast-forward-only/`--force`/`--dry-run`/`--repo`/`--branch`, the doctor
"Bare staleness" note, and docs. The plan's unit and integration verification items are mostly covered
(see Testing for gaps).

### Findings

1. **[Medium] `tmux_dispatch`: a code-repo fetch failure aborts the prompt dispatch.** Clarification 9
   says failures are downgraded to a warning and never fail the dispatch. Instead, the new loop sits
   inside the existing `try` that `return 1`s on `CalledProcessError`. The error message also names the
   *docs* repo path (`git sync failed in {repo_path}`), not the code repo that failed. Give the
   code-repo loop its own `try` per repo that prints a yellow warning naming `code_repo_path`.
   (`workflow/tmux_dispatch.py:287-302`)

2. **[Medium] `sync` includes repos where bare is *supposed* to be ahead of origin, and suggests a
   destructive fix.** `_sync_default_repos` adds `docs` whenever canon's docs repo has an `origin`.
   `sync` also doesn't reject in-band projects, even though `cli.rst` says "Out-of-band only". In-band,
   `layout.repos() == [docs]` is the canon root, whose `origin` is usually the real upstream. In both
   cases `bare/main` is the workflow's own `main`. It normally carries transition and accept commits
   that `origin` doesn't have yet, so a plain `workflow sync` does two bad things:
   - (a) it prints a refusal and exits 1 on every run;
   - (b) the refusal says "rerun with --force to overwrite". Doing that force-pushes `origin/main`
     over `bare/main` and throws away accepted plan history. This is exactly the data-loss path
     Risk 2 warns about.

   Suggested fix: reject `sync` in in-band mode, and either drop `docs` from the default set (require
   `--repo docs` explicitly) or never apply `--force` to docs.
   (`workflow/commands/workflow.py:961-1062`)

3. **[Medium] Pushing a code repo can fail *after* the docs handoff has already landed, and there is no
   in-tool way to recover.**
   - Detached HEAD: agents check out `base: 7f3a91c`-style commits. If they commit on a detached HEAD,
     `_compute_push_set` records `branch="HEAD"` (from `git rev-parse --abbrev-ref`), and
     `git push -u bare HEAD` fails. This happens only after `_transition_stack_members` and
     `git_push(docs)` have already run.
   - Non-fast-forward: if the reviewer (or the builder, in a later stacked plan) rebases a code branch
     that is already in bare, the plain `git_push_branch` is rejected. `accept --force-push` is not
     passed on to `_run_repo_push_set`, so rerunning the command can't fix it. The operator has to
     push by hand from the agent's clone.

   Suggested fix: add a classify-time precondition that each push-set entry is on a named branch. For
   the non-fast-forward case, either pass `force_push` through (`--force-with-lease`) or detect it up
   front with `git_is_ancestor(bare/<branch>, HEAD)` and fail before anything is transitioned.
   (`workflow/commands/workflow.py:1370-1395`, `2500`)

4. **[Low] If an agent commits straight onto a code repo's default branch, `sync` stops working for
   that repo.** When the builder commits on `main` in `mypackage`, `check` pushes it to
   `bare/mypackage main`. From then on `sync` refuses that repo (bare is not an ancestor of origin),
   and `--force` would discard the builder's work. Consider a warning in the push-set table when
   `info.branch` equals the upstream default branch of a code repo.

5. **[Low] `resolve_upstream_default_branch` mangles default-branch names that contain a slash.**
   `rsplit("/", 1)[-1]` turns `refs/remotes/origin/release/2.x` into `2.x`. Use
   `removeprefix("refs/remotes/origin/")` instead. (`workflow/git_helpers.py:~372`)

6. **[Low] `sync` does nothing, silently, when the resolved default branch is missing on origin.** For
   example, `origin/HEAD` points at a branch that was since pruned. The `continue` for
   `branch == default_branch` prints nothing, so the repo looks synced. It should print a warning.
   (`_sync_one_repo`)

7. **[Low] Missing clones cause tracebacks.** `_compute_push_set` (unlike `_require_clean_repos` and
   `_fetch_code_repos`) has no `is_dir()` guard. A missing code clone makes `run_command` raise
   `FileNotFoundError` from the missing `cwd`, which the handlers (`CalledProcessError` /
   `WorkflowError` only) don't catch.

8. **[Low] DRY.** `_classify_accept_steps` repeats `_classify_push_set_steps` inline instead of
   calling it (`workflow/commands/workflow.py:2434-2436`). `doctor._commits_between` is a raw
   `rev-list --count` subprocess that belongs in `git_helpers` next to `git_commits_not_in_bare`.

9. **[Low] Stale docstring.** `_run_pre_commit_hook` still says *repo* is "unused so far … wired up
   in 023.5". (`workflow/commands/workflow.py:236-241`)

10. **[Low / note] In-band `check` output has changed, contrary to the plan's "byte-for-byte
    unchanged".** In-band `check`/`accept` now print a "Repos ahead of bare" table and enforce the
    tracked/untracked dirty precondition. Both are reasonable, but record them as intended in-band
    changes in the plan or docs.

11. **[Note] `accept` never runs the per-repo hook on code-repo commits the reviewer added.** The only
    hook `accept` runs is the docs `post_rebase_verify`. This matches the plan (hooks run on `check`
    only), but it is a quality-gate gap worth an explicit decision.

### Testing

- The `accept` multi-repo push isn't tested at all. `test_oob_handoff.py` covers only `check`, and the
  `test_workflow_commands.py` changes only add mocks.
- The fetch-all in `tmux_dispatch` and the code-repo fetch in `_sync_repos_best_effort` are untested.
  This is the plan's "single most valuable line of defence".
- The per-repo hook fan-out is never asserted: no check that `--repo dep1` / `--repo docs` reach the
  docker script, or that `run_hook: false` skips a repo.
- `test_check_pushes_exactly_the_committed_repos…` asserts `_contains(output, "dep1")`, which proves
  little because "dep1" shows up in the output anyway. Assert the `push dep1` resume step instead.
- `_run_check` mocks `run_validate`, so the oob e2e path never runs the real validate. That is how
  023.6 B1 went unnoticed.
- `sync --dry-run` "mutates nothing" is only true for bare. Canon's remote-tracking refs are fetched
  for real, which the code comment documents. Fine, but the test name overstates it.

## 023.6 — validate, doctor, `info` matrix, frontmatter

### Spec coverage

Implemented: `CheckResult.repo`, per-repo `file-scope`/`git-hooks`, `planner-code-commits`,
`branches-frontmatter`, a mode-aware check list, `RepoBranch | None`, the v2 hash file covering
`.workflow.json`, the oob paragraph in the AGENTS.md template, doctor's per-repo rows plus the
single-remote and AGENTS.md-copy checks plus the dirty split, the `status` matrix, the `make_project`
fixture, and docs.

Partial or missing:

- `test_validate.py` and `test_doctor.py` are not parameterised over both modes as the plan requires.
  Separate `*_oob.py` files were added instead.
- There is no in-band regression test that `validate` returns exactly the four legacy results.
- The `.workflow.json` hash is recorded but never enforced (finding M1).

### Blockers

**B1. `git-hooks` fails every repo that doesn't ship `.git-pre-commit-hook`, i.e. the default oob
project, and so blocks `todo` and `check`.** Reproduced: after `init --oob` with no `hook_repos`,
`validate` reports `git-hooks … fail "pre-commit: not a symlink"` for `docs`, `dep1` and `mypackage`.

`_managed_hook_issues` requires `.git/hooks/pre-commit` to be a symlink to
`<repo>/.git-pre-commit-hook` in every repo with `run_hook`, which is the default (`true`). But
023.4's `_wants_hook_symlink` installs that symlink only when the repo actually contains
`.git-pre-commit-hook`. Its docstring says: "none of them (docs included) are guaranteed to ship
`.git-pre-commit-hook`".

The same code path defeats the plan's "husky / pre-commit framework is only a warning" rule. Such
hooks live at `.git/hooks/pre-commit`, a name in `managed_hooks`, so they fail as "not a symlink"
instead of downgrading to a warning. Because `todo` validates the planner (line 1281) and `check`
validates the builder, the oob pipeline can't advance without `--force-validation`.

Fix: in oob, run `_managed_hook_issues` for a repo only when `.git-pre-commit-hook` exists in it
(the same predicate as `_wants_hook_symlink`; reuse it). Otherwise treat an executable `pre-commit`
in a code repo as a routine third-party hook (warning).

Why the tests missed it: `test_validate_oob._setup_project` passes
`hook_repos=("mypackage", "dep1")`, so every code repo gets the symlink, and the docs repo happens to
pass. Add a test with the default fixture, and one where a code repo carries its own executable
`pre-commit`.

**B2. `doctor` applies docs-repo branch rules to code repos, so it exits 1 during normal oob work.**
Reproduced: builder `mypackage` on `feature/widget` gives the anomaly
`stray branch 'feature/widget': no plan is implementing/checking on it`, and canon `dep1` on `dev`
gives `expected 'main', on 'dev'`.

`_check_worktree` runs the canon-must-be-on-`main` rule, the builder/reviewer stray-branch rule
(against `_active_branches`, which holds only docs `feat/*`/`plan/*` names) and `_check_staleness`
(local `main` vs `bare/main`) for every `(worktree, repo)`.

For code repos all three are wrong:
- the tool doesn't manage code branches (intent, "Git branch model");
- the upstream default branch may be `master`/`develop`;
- the tool never runs `refresh_main` in a code repo, so every agent's local `main` goes stale after
  the first `workflow sync`, and canon's local `main` tracks `origin` and is routinely ahead of bare.

Fix: for `repo != DOCS_REPO`, skip the branch-name rules and `_check_staleness`. Keep the checks that
the clone exists and is valid, the index lock, the remote checks, and the dirty checks.

Why the tests missed it: `test_doctor_oob` only covers a freshly initialised project where every
repo sits on `main`.

### High

**H1. The "behind bare" count in the `status` matrix is meaningless.** `git_commits_behind_bare` runs
`rev-list --count --remotes=bare --not HEAD`, which counts every commit in *any* bare ref that HEAD
lacks. In the docs repo that includes every other in-flight `feat/*`/`plan/*` branch. In a code repo
it includes every agent's pushed feature branch and every synced upstream branch. The number grows
with unrelated parallel work, not with how stale this checkout is.

The docstring ("what a `workflow sync` would bring in") is also wrong: sync moves origin into bare,
not bare into HEAD.

Use the branch's own counterpart instead: `HEAD..@{u}`, or `HEAD..bare/<branch>` when that exists,
else show `-`. `info.py`'s matrix test asserts only that the names appear, never the cell contents.
(`workflow/git_helpers.py:176-189`, `workflow/commands/info.py:128-153`)

### Medium

**M1. The `.workflow.json` hash is stored but never enforced, and `add-repo` leaves AGENTS.md
stale.** `workflow_json_sha` is consulted only in `_stale_hash_inputs`, which adds a hint to the
message *after* an AGENTS.md hash mismatch. Pass/fail still depends solely on `agents_md_sha`.
`add-repo` neither regenerates AGENTS.md nor causes a mismatch.

Result: after `add-repo dep3`, every AGENTS.md copy still lists only the old repos in its
frontmatter instructions and `validate`/`doctor` stay green, while `branches-frontmatter` now demands
a `dep3` entry the agents were never told about. Risk 3 of the plan and the docs ("part of what a
drifted-AGENTS.md check protects") both assume the check fails. Either fail `agents-md` when the
recorded `config_yaml_sha`/`workflow_json_sha` differ from the current files, or have `add-repo` run
the AGENTS.md step.

Related bug: in-band `init` generates AGENTS.md (and the hash file) *before* `write_metadata`
(workflow.py ~790 vs ~797). Every in-band hash file therefore records `sha256(b"")` for
`.workflow.json`. Any later AGENTS.md drift in-band is then misattributed to
"`.workflow.json (e.g. add-repo) changed`", although `add-repo` doesn't exist in-band. Consider
hashing `.workflow.json` only in oob, or writing the metadata first.

**M2. `status` and oob `validate` crash with a traceback when a clone is missing.**
`_git_status_matrix` and `_validate_oob` call git in each `layout.git_repo_root(worktree, repo)` with
no `is_dir()` guard, and a missing `cwd` raises `FileNotFoundError`, which nobody catches. A missing
clone is precisely what `doctor` exists to diagnose, so `status` should render `missing` in that cell.

### Low

1. **DRY.**
   - `_check_agents_md_oob` (validate) and `_agents_md_hash_anomalies` (doctor) both hash every
     worktree-root AGENTS.md against the trusted value. Extract one helper that returns the mismatch
     list.
   - `validate._repo_runs_hook` re-implements `ProjectMetadata.runs_hook` (023.5's notes explicitly
     point at the latter).
   - `_is_allowed_oob_docs` copies `_is_allowed` with a different plans prefix. The plan asked for
     "the current rules with `plans_prefix`". Parameterise `_is_allowed` by `layout.plans_prefix` and
     add the reserved-root-file rule.
2. **Oob fallback for custom agent names.** A custom agent name falls back to `_validate_in_band`,
   which diffs `project_dir/<name>` (not a git repo in oob) with in-band `docs/plans` scope rules. That
   is wrong in oob and unrequested. Failing fast (or treating the name as `canon`) would be simpler
   and correct. (`validate.py:139-146`)
3. **`branches-frontmatter` ignores keys that aren't registered repos.** A typo like `mypackge:`
   yields "missing entry for 'mypackage'", which is fine, but a stray `dep9:` for an unregistered
   repo passes silently. Consider flagging unknown keys other than `docs`; this is cheap and still
   within decision 14.
4. **`noqa-nosec` in code repos uses `git log -p` (per-commit patches).** A `noqa` added in one commit
   and removed in a later one is still reported. This is acceptable as a warning, but mention it in
   the Risk 1 docs paragraph.
5. **Naming: "Bare staleness" notes go through `_print_anomaly_section`.** Rename the helper (e.g.
   `_print_section`), since these are notes, not anomalies.
6. **`render_workflow_section` checks `config.metadata is not None` twice** (once for `oob`, again
   for `code_repos`). Compute `code_repos` inside one `if`.

### Documentation

- `workflow.rst` says "`workflow check`/`workflow accept`'s `validate` step", but `accept` doesn't run
  validate. `todo` does, on the planner, and that matters for B1.
- `workflow.rst` claims `.workflow.json` is "part of what a drifted-AGENTS.md check protects". That is
  false today (M1).
- The RST title underline for "Multi-repo validate, doctor, and status" is 38 characters for a
  39-character title, so Sphinx warns "Title underline too short".
- The v1 to v2 hash-file bump makes `validate` fail on *every* existing project, in-band included,
  until the operator runs `workflow agents_md`. The error message says so, but the change isn't listed
  as an upgrade step next to the `migrate_023.py` post-completion tasks.
- Risk 1 (code-repo validate reports all unpushed commits, not a branch diff) is covered only
  implicitly. Add one explicit sentence.

### Testing

- Fixtures mask real behaviour: `hook_repos=` hides B1, and "all repos on `main`" hides B2. Add oob
  tests with default init, with a code repo on a feature branch, with canon on `master`, and with
  local `main` behind bare after a sync.
- No doctor tests for: the AGENTS.md drift anomaly, a missing hash file, the tracked-dirty anomaly vs
  the untracked-only note (a behaviour change for in-band too), or an agent code repo with zero
  remotes.
- `status` matrix: assert the actual cell values (`branch +N/-M`, `*` on tracked-dirty), not just the
  header names.
- New `git_helpers` functions have no unit tests: `git_commits_behind_bare`,
  `git_changed_files_not_in_bare`, `git_diff_text_not_in_bare`, `git_check_ref_format` (edge cases:
  `-foo`, `a..b`, `HEAD`, `@{-1}`), and `git_list_remotes`.
- Add an in-band regression test that `validate` returns exactly the four legacy results, with
  `repo=None` on each.
- `branches-frontmatter`: add cases for an invalid branch name, a plan in `planning` (not required),
  and a `null` entry.
- The plan asked for `test_validate.py` and `test_doctor.py` themselves to be parameterised over
  modes; that wasn't done.
