## 023.4 — `init --oob`, `add-repo`, AGENTS.md, venv bootstrap

### H1. Wiring canon points the operator's code repos at `bare` for upstream tracking and push config [verified]
`_wire_canon_to_bare` (`workflow/commands/workflow.py:344`) is now used for every oob repo.
It runs `git push -u bare HEAD` and sets `push.default=current` / `push.autoSetupRemote=true` in
`canon/<code_repo>`. These are the operator's own clones, and they already track the real upstream.
Reproduced: `main@{upstream}` goes from `origin/main` to `bare/main`. After `init --oob`:
- `git pull` in `canon/mypackage` pulls from the private bare instead of upstream;
- `git push` (with `push.default=current` plus the rewritten `branch.main.remote`) pushes to
  `bare`, not to the operator's fork.

This contradicts intent decision 10: code repos keep "their own upstream remotes", and
`origin`/`upstream` keep their conventional meanings. It also undermines 023.5's `workflow sync`,
which relies on canon's upstream. Nothing in the output mentions the change.
Fix: for code repos, add the remote and push without `-u` (`git push bare HEAD` or an explicit
branch refspec). Leave the operator's push config alone. The docs repo can keep today's behaviour,
since canon's docs `main` is expected to track `bare`. Add a test asserting that a canon code
repo's `@{upstream}` is unchanged after `init --oob` and after `add-repo`.

### H2. `--skip-hook` does not skip the hook symlink, despite its help text and docs [verified]
The `--skip-hook` help on `init` and `add-repo` and `docs/source/cli.rst` all say it skips
installing the pre-commit hook symlink. In the code it only sets `CodeRepoMeta.run_hook=False`.
`_ensure_agent_repo_configure` / `_agent_repo_configure_ok` never look at `run_hook`, and they
install the symlink whenever `.git-pre-commit-hook` exists. Reproduced: a code repo that ships
`.git-pre-commit-hook` and is passed `--skip-hook` still gets `.git/hooks/pre-commit` in every
agent clone, with `run_hook: false` recorded. Nothing in `workflow/` reads `run_hook`.
`test_skip_hook_is_recorded_and_no_symlink_installed` passes only because its repo has no hook
file, so the skip part of the test proves nothing.
Decide what `run_hook` means. Intent decision 12/15 reads as "whether the workflow's pre-commit
check runs for this repo", which lands in 023.5. Then either:
- also honour it when installing the symlink, or
- reword the help text and docs to "do not run the pre-commit check for this repo".

Either way, fix the test so the repo actually has a `.git-pre-commit-hook`.

### M1. `--skip-hook` names are not validated [verified]
- A typo (`--skip-hook mypackge`) is silently ignored: init exits 0 with `run_hook: true`.
- On resume (the `.workflow.json` already exists), `--skip-hook` values are ignored silently.
  Deviation 3 explains why the old list is reused, but a flag that has no effect should fail or warn.

Fix: `require(skip_hooks <= detected_names, ...)`, and reject (or warn about) `--skip-hook` when
the metadata already exists.

### M2. Code repo names are not validated (`add-repo NAME`, `CodeRepoMeta.name`) [verified]
- `add-repo sub/nested` is accepted. It is registered as `sub/nested` and cloned into
  `bare/sub/nested`, `planner/sub/nested`, and so on.
- `add-repo ../outside` is rejected only by accident: `canon/../outside` and `bare/../outside`
  resolve to the same directory, which then fails the "valid bare clone" check with a confusing
  message.
- `.workflow.json` is tool-owned, but the model itself does not reject duplicate names or `docs`.
  `add-repo` checks both; `init`'s scan cannot produce them. The rule should live in one place,
  the model.

This is a trust boundary (CLI input that becomes filesystem paths).
Fix: validate `CodeRepoMeta.name` as a single, safe path component, e.g.
`^[A-Za-z0-9][A-Za-z0-9._-]*$`, not `docs`, no `/`. Add a `ProjectMetadata` validator for unique
names. Drop the ad-hoc duplicate/`docs` checks in `_check_add_repo_preconditions`, or keep them
only for the nicer message.

### M3. The oob preconditions do not check that the docs repo has `main` checked out [verified]
The whole docs state machine assumes `main` (`refresh_main`, `bare/main`, transfers, and doctor's
"canon expected on 'main'"). An operator who ran `git init` with a `master` default gets a
successful `init --oob`. Reproduced: exit 0, and `bare/docs` gets `HEAD -> master`.
The first `todo`/`implement` then fails far from the cause.
Fix: require `git_current_branch(docs_repo) == "main"` in `_check_oob_init_preconditions`.

### M4. `bootstrap_venv.sh` is only checked in canon's working tree, not in what was committed
The precondition checks `is_file()` and `os.access(X_OK)` on `canon/docs/bootstrap_venv.sh`.
Agent worktrees get the docs repo by cloning, so they only see what was **committed**, with the
**committed** file mode. An uncommitted script, or one committed as 100644, passes init. The
agents' `venv` step then falls back to `uv venv && uv sync` at a wrapper root with no
`pyproject.toml`, or fails on `./docs/bootstrap_venv.sh: Permission denied`. That is exactly the
late failure the precondition exists to prevent (plan: "failure is at init, not at first `venv`").
`body_of_agents.md` has no such problem (it is read from canon), but it should still be committed
for the "body under version control" property.
Fix: check `git ls-files -s bootstrap_venv.sh` in `canon/docs` reports mode `100755`, or at least
that the file is tracked and clean.

### M5. `agents_md` in oob treats a missing body as empty and overwrites all four copies
`prepare_agents_md_update` reads `body_of_agents.md` as `""` when the file is absent, and
`test_prepare_agents_md_update_oob_missing_body_starts_fresh` makes that behaviour intentional.
After init this is data loss: if the body is renamed, deleted, or missing on canon's checked-out
branch, `workflow agents_md` quietly rewrites all four `AGENTS.md` copies (and the hash) with only
the managed section. The hand-written instructions disappear from every agent's context.
In-band has the same fallback, but there the body *is* the target file, so nothing is lost.
Fix: in oob, raise `AgentsMdGenerationError` when the body file is missing, and replace the test.

### M6. Hook contract in oob: venv activation and the "docs-repo default" comment
- The `hook` subcommand now `cd`s into `${REPO_PATH}/${CODE_REPO}`, but the single `.venv` sits at
  the wrapper root. Tools inside a hook (`uv run`, or anything relying on `.venv` next to
  `pyproject.toml` or in the cwd) will not find it. The script does not export
  `VIRTUAL_ENV`/`PATH` for the wrapper venv. It works in-band only because the venv and the
  workdir coincide.
- The comment on `--repo` in `docs/example_run_agent_in_docker.sh` says the default mount-root
  workdir covers "an oob docs-repo hook". It does not: the oob wrapper root is not a git repo, so
  the docs hook must be run with `--repo docs`, and without it the script reports "no pre-commit
  hook found".

Both matter as soon as 023.5 wires up per-repo hooks. Fix the comment now. Either activate the
wrapper venv in `HOOK_CMD` (e.g. `source "$REPO_PATH/.venv/bin/activate"` when present) or record
the gap as an open item in 023.5.

## 023.2 — Layout and vocabulary

### M7. `Layout.code_repos()` in-band semantics differ from the plan, and the deviation is not recorded
The plan's inventory spec says in-band `code_repos()` returns `[DOCS_REPO]` (the single repo *is*
the code repo). The implementation returns `[]`, and its docstring says so. The difference matters
for 023.5: "push every code repo ahead of bare" and "dirty checks across code repos" behave
differently depending on which is meant. Record the decision in 023.2's Deviations, and make sure
023.5 is written against the actual semantics.

### M8. The migration only rewrites the project-level `config.yaml`
`load_config` resolves config from `--config`, then `{project}/config.yaml`, then
`~/.config/workflow/config.yaml`. `migrate_config_worktree_override_key` only looks at
`{project}/config.yaml`. A user-level or `--config` file that still has `repo_override` fails with
the new validator message, and that message sends the operator to the migration script, which
reports "not present; skipping". Either migrate the user-level file too (or accept a
`--config PATH`), or make the validator message say which file it rejected.

### L — 023.2
1. The completion-criterion grep still matches outside `layout.py`:
   `workflow/commands/workflow.py:787` `canon_root = project_dir / WorktreeName.canon.value`.
   This is chicken-and-egg (init has no metadata yet), but a default-metadata
   `Layout(...).worktree_root(canon)` avoids the raw join.
2. `state.transition_plan` builds `new_path` with hardcoded `"docs" / "plans"`. It is correct in
   both modes, but it is exactly the kind of literal Risk 2 says should come from `layout`, e.g.
   `layout.plans_root(worktree).relative_to(layout.project_dir)`.
3. Wrong accessor for git operations. `doctor._check_worktree(..., layout.worktree_root(wt))` and
   `info status` → `git_status(layout.worktree_root(wt))` run git in `worktree_root`. The meaning
   is `git_repo_root`: identical in-band, wrong in oob (the wrapper is not a repo, so doctor will
   report "no 'bare' remote" for every oob worktree). 023.6 will touch this, but the 023.2 contract
   was one accessor per meaning.
4. The vocabulary rename is incomplete:
   - the doctor table column is still `"repo"` (the plan asks for `worktree`);
   - `_check_worktree(repo_name, repo_path)` keeps the old names;
   - `_run_pre_commit_hook(config, repo_name, ..., repo=)`, `_hook_command(..., repo_name, repo=)`
     and `_create_venv_command(..., repo_name)` use `repo_name` for a *worktree* right next to the
     new `repo` meaning a *git repo*. That is the exact collision this plan set out to remove.
5. `Layout.hook_root` is unused so far (planned for 023.5; fine, just noting it).

## Addendum: is it safe to merge and migrate in-band projects before 023.5/023.6?

Yes, once H1/H2/M1–M8 are fixed and the steps below are followed. In-band path math is identical
under `Layout`, and the unfinished oob behaviour is only reachable through `init --oob`/`add-repo`.
`_hook_command` only adds `--repo` when a caller passes it, and no in-band caller does, so
customised `run_agent_in_docker.sh` copies keep working for in-band projects without changes.
The migration is one-way, and several things outside its reach still say `origin`:

1. **Prompt text in each project's `config.yaml`.** The `rebase` prompts copied from
   `default_config.yaml` say "Fetch from origin and rebase onto `origin/main`". Migration step 2
   only renames the `repo_override` key, so after the remote rename those prompts send agents to a
   remote that no longer exists. Fix: extend step 2 to report or replace `origin/main` in prompt
   text, or document it as a manual step.
2. **Agent system prompts outside the repo.** `~/.pi/agent/SYSTEM.md` (lines 417–419, the
   reviewer's "Your Process") runs `git diff origin/main...`, and the planner/builder prompts are
   probably similar. The `pr` step breaks until these are changed to `bare/main`. Update them by
   hand, as part of the operator's post-completion tasks.
3. **The AGENTS.md hash will mismatch.** Migration rewrites `config.yaml` (which is part of the
   hash) and the template gained a sentence, so `validate`'s agents-md check fails until
   `workflow agents_md` is re-run in canon and committed/pushed.
4. **Order of operations for this repo (self-hosting).** `accept` this branch with the *old*
   code (it still expects `origin`). Then:
   - stop the tmux session;
   - update the installed `workflow`;
   - run `scripts/migrate_023.py --project-dir <project>` (use `--dry-run` first);
   - run `workflow agents_md` and commit it;
   - run `workflow doctor` and expect it to be clean;
   - restart.

   Running old code after the migration, or new code before it, fails loudly but safely: the old
   code reports a missing `origin`, and the new code reports the legacy marker or the old config
   key.
5. **In-flight work.** The migration re-points every branch that tracked `origin` (tested for a
   feature branch as well as `main`), so plans in `todo`/`implementing`/`checking` survive. Have no
   agent mid-command while it runs.
6. **No rollback script.** Reverting the code after migrating means undoing the migration by hand:
   `git remote rename bare origin` in canon and every agent clone, re-set upstreams, recreate
   `.workflow_root`, and rename `worktree_override` back to `repo_override`. Back up the project's
   `config.yaml`, or keep this list, before migrating.
