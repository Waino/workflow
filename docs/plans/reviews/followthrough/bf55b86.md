## 1. `workflow go` command — not implemented

**Source:** intent/011_tmux_pane_rotation.md

A `go` subcommand is specified for rotating the human's control pane between agent
windows (`planner`, `builder`, `reviewer`, `manual`).  The intent file contains a
manually-verified proof-of-concept Python script using libtmux `join-pane`.  The
command is not registered anywhere in the workflow CLI and does not appear in the
script registry.

## 2. `workflow start` — split-pane control layout not created

**Source:** intent/011_tmux_pane_rotation.md, intent/001_idea.md

The `start` command creates one tmux window per agent via `new-window` and launches
Docker containers, but it does not create the side-by-side split that the intent
requires: each agent window should have two panes — the agent's pane (right) and a
docked control pane (left) that `workflow go` moves between windows.  Without this
layout `workflow go` cannot function.

## 3. `workflow implement` — builder tmux switch and branch setup not implemented

**Source:** intent/001_idea.md, workflow/commands/workflow.py line 395

After transitioning the plan state to `implementing` and pushing master, the command
should:

- switch to the builder's tmux window so the human is looking at the builder
- (implicitly) leave the builder ready on a feature branch

A `# TODO: switch to the builder tmux window.` comment marks the gap.  No fetch or
feature-branch creation in the builder repo is performed either.

## 4. `workflow check` — reviewer pane rotation not implemented

**Source:** intent/001_idea.md, intent/013_example_walkthrough.md

After handing off to the reviewer (push builder branch, fetch in reviewer), the
command should rotate the tmux panes so the reviewer's window is visible.  Currently
only `git fetch` in the reviewer repo is performed; no pane rotation occurs.

## 5. `workflow reject` — push not performed

**Source:** intent/001_idea.md, workflow/commands/workflow.py

The `reject` command transitions the plan state and commits to `--target-repo`
(default: `master`), but never pushes.  The rejection is therefore not propagated to
the bare repo or to the other agent clones.  Compare with `todo` and `accept`, both
of which call `git_push` after committing.

---

## 6. Review path fuzzy resolution — not implemented

**Source:** done/012_plan_resolution_respec.md, workflow/plan_resolver.py lines 895-897

`resolve_plan()` detects fuzzy paths containing a `reviews/` segment and raises
`PlanNotFoundError` with the comment *"Reviews are resolved by a separate entry point
(not yet implemented)."*  Absolute-path resolution for reviews works correctly, but
short-form references such as `reviews/pr/007` or `007` when the plan is in review
state cannot be resolved.

## 7. `full review` prompt — incomplete relative to spec

**Source:** intent/018_prompts.md, docs/default_config.yaml

The `review` state's `full review` prompt in `default_config.yaml` reads:

> Perform a full review of the current state of the codebase.
> Search for dead code, propose integration tests, and review overall architecture.
> Write a report into docs/plans/reviews/full/.

Intent/018 specifies a detailed checklist across eight categories: architecture
smells, functional correctness, error handling gaps, Pydantic usage, async misuse,
dead code via `vulture`, testing quality, documentation quality, and miscellaneous
concerns (naming, verbose logging, long string literals, etc.).  The current prompt
covers only three of those categories in broad strokes.
