# 023.4: `init --oob`, `add-repo`, AGENTS.md generation, venv bootstrap

Input: `intent/023_out_of_band`, `planning/023.3_bare_remote_rename`
Completeness: complete

## Goal

Make it possible to *create* an out-of-band project: one bare repo and one clone per component,
a `docs` repo holding the plans, an unversioned generated `AGENTS.md` at each worktree root, and a
single wrapper-level venv. Also add `add-repo` so a code repo can be registered after init, since
`.workflow.json` is not hand-editable.

## Scope

In scope: `init --oob` (+ mode immutability), `workflow add-repo`, oob AGENTS.md generation from a
versioned body, venv bootstrap via a docs-repo script, `run_agent_in_docker.sh` argument changes,
init preconditions and per-repo hook handling.

Out of scope: multi-repo behaviour of `check`/`accept`/`sync`/`fetch` (023.5); `validate`/`doctor`
/`info` (023.6). Repo *removal* is out of scope permanently for now.

## Design

### `init --oob`

Operator prerequisites (checked as preconditions, not created by the tool):
- `canon/docs/` is a git repo with at least one commit;
- at least one further `canon/<name>/` git repo with at least one commit (the code repos);
- `canon/docs/body_of_agents.md` exists;
- `canon/docs/bootstrap_venv.sh` exists and is executable;
- `env.list` exists (unchanged);
- no leftover `.git/index.lock` in any repo.

Behaviour:
1. Detect code repos by scanning `canon/*/` for `.git`, excluding `docs`. Record them in
   `.workflow.json` with `run_hook = name not in --skip-hook`. (Decision 1 — "store, not discover" —
   governs the ongoing source of truth: after init, only `.workflow.json` is consulted; scanning is
   a one-time convenience at registration time.) Print the registered list.
2. Create `bare/<repo>` for every repo (`git clone --bare canon/<repo> bare/<repo>`).
3. Wire each `canon/<repo>` to its bare (`git remote add bare ...`, `git push -u bare HEAD`).
4. Clone every repo into every agent worktree: `git clone -o bare bare/<repo> <agent>/<repo>`.
5. Configure push behaviour per repo; install the pre-commit symlink **only** where
   `<repo>/.git-pre-commit-hook` exists (third-party repos will not have one).
6. `.gitkeep` state dirs inside the docs repo (`layout.plans_root(canon)`).
7. Write `.workflow.json` (mode + code repos).
8. Generate `AGENTS.md` into every worktree root (see below) — after the clones, not before, since
   in oob mode it is not propagated by git.
9. Create the venv per worktree via the docker script.

Mode immutability (decision 13): if `.workflow.json` exists and its `mode` differs from the invoked
flag, fail with
`"project was initialised in {existing} mode; --oob cannot be changed after init"`. In-band init is
unchanged apart from this check and the metadata write from 023.1.

`--skip-hook NAME` is repeatable and only valid with `--oob`.

Structure the classify/run split exactly as today (`_classify_*`/`resume.should_run`), with the
per-repo steps named `f"bare clone {repo}"`, `f"clone {agent}/{repo}"`, `f"configure {agent}/{repo}"`.
Mode-specific step sets are fine; the step-name constants stay the join key.

### `workflow add-repo NAME [--skip-hook]`

Registers an additional code repo in an oob project. Preconditions: oob mode; `canon/NAME` is a git
repo with a commit; `NAME` not already in `.workflow.json`; `NAME != "docs"`. Steps: create
`bare/NAME`, wire canon, clone into each agent worktree, configure push/hook, append to
`.workflow.json` (atomic write). Fails in in-band mode with a clear message. Same
classify/resume treatment as `init`.

Register it as a script command in `docs/default_config.yaml`? No — it is a project-setup command
like `init`, so it needs no state entry; expose it as a plain CLI script command available outside
the state machine (same treatment as `doctor`).

### AGENTS.md in oob mode

Today the hand-written body lives *in* `canon/AGENTS.md` and `workflow agents_md` splices the managed
section into it. In oob mode the worktree root belongs to no repo, so:

- the body is version controlled in the docs repo as `docs/body_of_agents.md`;
- `prepare_agents_md_update` reads the existing body from
  `layout.git_repo_root(canon, DOCS_REPO) / "body_of_agents.md"` instead of from the target file, and
  the managed section is *appended* to it (the body must not contain markers — reject if it does);
- the rendered result is written to **all four** worktree roots (`canon`, `planner`, `builder`,
  `reviewer`), because git no longer propagates it;
- the `.agents_md_hash` file is unchanged (one hash; all copies are byte-identical);
- nothing is committed for AGENTS.md in oob mode (there is no repo to commit it to); the body file is
  committed by the planner like any other docs change.
- the managed section gains a sentence stating that these workflow rules override any repo-local
  `AGENTS.md` (decision 18). This applies in both modes and is a template change in
  `workflow/templates/agents_md_workflow.md.j2`.

In-band behaviour is unchanged: body = existing `canon/AGENTS.md`, single target, committed.

Implementation shape: keep one `prepare_agents_md_update` returning a list of write targets plus the
body source, with the two modes differing only in those inputs. Resist a second code path.

### Venv bootstrap (option B, chosen)

`docs/bootstrap_venv.sh` (in the docs repo, executable) creates the wrapper-level `.venv` and installs
all code repos in editable mode. Rationale over the alternatives is recorded in the intent file.

- `docs/example_run_agent_in_docker.sh`: the `venv` subcommand runs `./docs/bootstrap_venv.sh` from
  the mount root when that file exists, else falls back to today's `uv venv --seed && uv sync`.
  Same fallback for the `canon` throwaway container.
- Ship an example `docs/example_bootstrap_venv.sh` in this repo (`uv venv --seed`, then
  `uv pip install -e <repo>` per code repo) and reference it from the docs.
- `init --oob` precondition checks its presence and executability, so failure is at init, not at
  first `venv`.

### `run_agent_in_docker.sh` contract change

The intent's claim that the script needs no major changes is wrong and has been corrected there.
Changes to `docs/example_run_agent_in_docker.sh`:

- new optional `--repo NAME` for the `hook` subcommand: sets the workdir to `${REPO_PATH}/${NAME}`
  (default: `${REPO_PATH}`, i.e. in-band);
- the `hook` subcommand runs `./.git-pre-commit-hook` when present, else `.git/hooks/pre-commit`
  when present, else exits with a clear error (decision 15);
- the `venv` subcommand runs the bootstrap script when present (above);
- `agent` and `shell` keep the wrapper root as workdir, so the generated `AGENTS.md` and all repos are
  visible to the agent.

Caller side: `_create_venv_command` unchanged; the hook invocation helper gains a `repo` argument
(its per-repo use lands in 023.5). Existing customized copies of the script in real projects must be
updated by the operator — post-completion task, listed in the final summary.

## Verification

- Integration test building a real oob project in `tmp_path`: three git repos under `canon/`
  (`docs`, `mypackage`, `dep1`), then `init --oob`; assert `bare/{docs,mypackage,dep1}` are valid
  bare repos, every worktree has all three clones each with a single `bare` remote, `.workflow.json`
  records the two code repos, and `AGENTS.md` exists at all four worktree roots with matching hashes.
- Resume test: re-running `init --oob` classifies every step `satisfied`/`needs_continue` and mutates
  nothing.
- `init` (in-band) on an oob project and `init --oob` on an in-band project both fail with the
  immutability message.
- `--skip-hook dep1` → `run_hook: false` in `.workflow.json`; a code repo without
  `.git-pre-commit-hook` gets no symlink and does not fail init.
- `add-repo`: happy path (dep2 registered, cloned everywhere, metadata updated); rejected in in-band
  mode; rejected for a duplicate name and for `docs`.
- AGENTS.md: oob generation from `body_of_agents.md` writes four identical copies and one hash file;
  a body containing workflow markers is rejected; in-band generation is byte-identical to today
  (regression test).
- Docker invocations stay mocked (no Docker in the sandbox); the example scripts are verified by
  `bash -n` syntax check plus review — note this limitation in the plan's completion report.
- `black`, `ruff`, `pytest`, `mypy --strict` green.

## Risks

1. **AGENTS.md is now an unversioned artifact in four places.** If one copy drifts (manual edit,
   half-finished `agents_md` run), agents disagree about their instructions. 023.6's doctor check for
   all four copies against the hash is the mitigation and should not be deferred further.
2. **`init --oob` is the longest step sequence in the tool** (repos × worktrees). Partial failure
   must leave a resumable state; the per-repo step naming is what makes that possible.
3. **Auto-detecting code repos at init** silently registers anything with a `.git` under `canon/`,
   including a stray clone. Print the list and require `--continue` when more than expected? Simpler:
   print the registered repos prominently; the operator sees them in the resume preview before
   anything is written.
4. **The bootstrap script is executed inside the container from a repo agents can write to.** That is
   no new authority (the agent already controls its sandbox), but the script must never be executed
   on the host — keep all invocation inside `run_agent_in_docker.sh`.
5. **`body_of_agents.md` lives in the docs repo**, so the docs repo is no longer plans-only; 023.6's
   file-scope rules must allow it (and `bootstrap_venv.sh`) or every planner branch will fail
   validate.
